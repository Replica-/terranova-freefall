# Porting notes

How the standalone build is put together, and what is left to do. (Steps 2 and 3 of the plan; see the README for the steps.)

## Two builds from one source tree

| | Verification build | Port build |
|---|---|---|
| How | `verify/build.sh` (gcc -m32, flat blob at 0x10000000) | CMake (`CMakeLists.txt`) |
| Runs | in the Unicorn emulator, next to the original `__FF.EXE` | as a normal 32-bit program |
| Defines | `TN_WATCOM_ABI`, `TN_LINK_ORIGINAL_DATA` | `TN_LINK_ORIGINAL_DATA` |
| Calls to/from original code | Watcom-convention thunks (`verify/gen_thunks.py`) | plain C calls |
| Globals | linker symbols at the original addresses | the same offsets inside `tn_data_obj` / `tn_code_obj` |

Every change for the port is behind `#ifdef TN_WATCOM_ABI` (verification) / `#else` (port), so the verification build stays byte-for-byte what was verified: `build/mine.bin` from this tree is identical to the one of the final decompilation run. Keep it that way. After any change to `src/` or `include/`, rebuild with `verify/build.sh` and rerun the suites that cover the change.

`WATCOM_CALL(f, ...)` (include/lg_types.h) is a register-convention call in the verification build and a plain call through a `long (*)()` pointer in the port.

## Original data without shipping it (`port/core/image.c`)

The decompiled C reads and writes about 2,450 globals of the original program (tables, strings, state), listed as `data` rows in `symbols/*.csv`. Their types are only partly known, and the code relies on their exact layout (neighbouring variables, pointer arithmetic). So the port keeps the layout:

1. `tools/gen_port.py` writes `tn_image.S`: two zero-filled arrays the size of the original code object (0x244000, 0x110940 bytes) and data object (0x355000, 0x10F900 bytes), and every data row as a symbol at its offset inside them.
2. At start-up `port_load_image()` reads the player's `__FF.EXE` (checked: English v1.09, size and CRC-32), copies both objects' pages into the arrays and applies the LE fixups. A pointer into the data object becomes `tn_data_obj + offset`. A pointer into the code object becomes our C function when a routine starts there (`port_funcs`, generated `tn_funcmap.c`), else `tn_code_obj + offset` (some data lives in the code segment).

Result on v1.09: 7,997 code pointers in the data object are translated to our functions. The bytes of the original machine code are loaded too (they sit around the data kept in the code segment), but never run.

Later, as the port drifts from the original (64-bit, new features), tables can move into C one by one; the image stays the reference.

## Original routines without a decompiled C version

`tools/gen_port.py` still generates a stand-in (`tn_stubs.c`: logs its first call, returns 0) for every `orig` function row that nothing in `port/` defines. A function written anywhere in `port/` replaces its stand-in automatically. At the end of step 3 there are **none left**:

| Original code | Port |
|---|---|
| Miles Sound System (the `AIL_*` routines) | `port/audio/miles.c` (samples, mixer, timers glue; the options' Music line switches the output at once, `port_music_reopen`, the sequencer replaying each channel's last state and held notes to the new one, `xmi_restore`), `port/audio/xmidi.c` (XMIDI sequencer at 120 Hz), `port/audio/fmsynth.c` + Nuked OPL3 (FM), `port/audio/gmout.c` (General MIDI), `port/audio/miles_timer.c` |
| Smacker | `port/video/smacker.c` (decoder and player) |
| UniVBE / VESA BIOS, VGA ports | `port/video/video.c`, `port/core/platform.c` (SDL3 window, palette, emulated status ports) |
| Watcom C library, DOS and DPMI calls | `port/core/files.c` (paths, Watcom text mode), `port/core/dosemu.c`, `port/core/compat.c`, host C library |
| Divide-error handler | `port/core/divtrap.c`: the CPU exception gives the original handler's saturated result. `fix_div` and every 64-bit division in the decompiled files divide with `idiv` (`port/core/idiv64.c`), so they overflow like the original |
| RSD8 bitmaps, water renderer, skeleton helpers, vector pictures, `fix_pow`, task 5 | `port/original/orig_2d.c`, `orig_skel.c`, `orig_vec.c`, `orig_extra.c`: C that follows the original instruction by instruction, checked in the emulator by `verify/test_port_orig.py` |
| `__prtf` (the game's `sprintf`), `fscanf` | `port/original/orig_crt.c`: host `vsnprintf` / `vfscanf` |
| Head trackers, Spaceball, VFX1, CyberMaxx | `port/original/orig_hw.c`: never detected |

The original's start-up runs the routines of its XI table before `main`; the port runs the ones it has (the EDMS physics constants, `port_static_init` in `port/core/image.c`).

The game's clock (`tn_ticks`, in milliseconds) was moved on 4 ms at a time by the original's 250 Hz timer, and the game times every frame by it. In the port the timer (`port/audio/miles_timer.c`, a thread that takes the interrupt lock) sets it to the real milliseconds since it started instead (`port_tick_sync` in `src/timer/timer.c`), and so do the start of each frame (`port_frame_limit`) and the end of a sharp 3D drawing, whose put-back of the game's data puts the clock back too. Frames that are not a whole number of 4 ms steps (60 a second) are then timed evenly (P55). The lockstep runs below keep their fixed clock.

At Frame rate 60 fps (`smooth_fps=true`, called Smooth frame rate before) the frames start on the display's refreshes (P57, P59): a refresh's length comes from the display's mode (`display_hz`: `SDL_GetCurrentDisplayMode` of the window's display, looked at every 2 s; the presents' average length when it has none), and the window's loop counts the refreshes by time as each `SDL_RenderPresent` returns (vsync; `display_refreshed`): a present that missed refreshes counts each one it missed, and the refreshes' start (`disp_phase`) follows the returns' times slowly. When the frame time is a whole number of refreshes to 2.5% (60, 120, 180, 240 Hz ... up to 8 refreshes) and the presents keep to the refreshes (their average at least 3/4 of one; with no vsync or a variable refresh they come faster), `port_frame_limit` sleeps until the refresh that many after the last frame's begins, by that clock, instead of its own clock, at most half a frame longer, so a display without vsync, a window being dragged or a slow frame never holds the game; a frame that starts late starts the count again from the refresh then. P57 counted the presents: at 240 Hz and 4K the window's work for a new picture took longer than a refresh, the presents came 180 to 210 a second, which matched no frame rate, and the frames ran on their own clock. The display shows the newest finished picture at each refresh; a frame started on its own clock finished at a different point of each refresh's time, and one a little slower than the rest came after its refresh.

## 3D register-call glue (`port/core/regcall.c`)

Parts of the 3D library were hand-written asm with their own register conventions. In the verification build the C of one 3D module calls another module's routine at its original address through `g3a_asm_call`, `g3b_call` or `tn3c_call`. In the port those helpers are a table: each routine's registers are mapped to its C arguments (32 routines). An unknown routine stops the game with a clear message. A call target is either an original address or one of our functions (a code pointer from the game's data); original routine addresses are recognised first. This needs our program to stay out of the original code's address range (0x244000-0x354940), so the Windows .exe is linked at a fixed 0x400000 with random placement (ASLR) off (P40); an unknown routine's message names the caller and its registers.

Assumption to confirm in the frame comparison: `g3_check_normal_facing`'s callers test the sign flag the asm left; the port sets it when the C result's bit 0 is set (the dot product is negative).

## Testing without a screen

`port/core/platform.c` reads a few environment variables meant for automated runs:
- `FREEFALL_SCRIPT="ms:action;..."` feeds input at the given times: `k<key>` (press and release, SDL key names), `d<key>` / `u<key>` (hold / release), `e<key>` / `a<key>` (key / Alt+key through the window's event queue, e.g. `aO` opens the options screen), `W<x>,<y>` (left click at window pixels through the event queue), `m<x>,<y>` (move the pointer, game pixels), `h<n>` (mouse wheel, 1 up, -1 down, through the event queue), `r<dx>,<dy>` (relative mouse motion through the event queue, for mouselook), `v<x>,<y>` (the real mouse to window pixels x,y: SDL's own motion), `c` (left click), `b<n>` (hold the game's mouse buttons: 1 left, 2 right, 0 none), `o<n>,<v>` (set the game's own option n to v, as the options screen does; 8 is the Difficulty level, 1 to 5), `q` (quit). A time written `+ms` counts from the moment a mission starts, and the script waits there until one does (the menus take longer on a loaded machine). Example to start a random scenario: `3000:kEscape;5000:kEscape;7000:kEscape;9000:kEscape;11000:m450,370;11500:c;14000:m320,456;14500:c;18000:m510,444;18500:c`.
- `FREEFALL_SHOT=prefix` and `FREEFALL_SHOT_EVERY=ms` save screenshots (BMP). `FREEFALL_SHOT_WINDOW=1` saves the whole window as shown (with the screen filters), `FREEFALL_WINDOW=WxH` sets the window's first size, and `FREEFALL_RENDERER=gpu` asks for SDL's GPU renderer even with no effect on. Headless on Linux, the GPU renderer runs on Mesa's lavapipe (`VK_ICD_FILENAMES=/usr/share/vulkan/icd.d/lvp_icd.json`).
- `FREEFALL_DEBUG_TICKS=1` logs the game tick and frame counters every second; `FREEFALL_TRACE_SOUND=1` logs the sound calls (and which music pack files play); `FREEFALL_SOUND_DUMP=file` writes everything the mixer outputs to that file (raw 44100 Hz, 16-bit stereo).
- Smoothness (`port/core/platform.c`): `FREEFALL_PRESENT_TIMES=1` logs the display thread's work per picture and how many refreshes each frame stayed up, each second; `FREEFALL_PACE=0` turns the frame pacing off. `FREEFALL_ML_TIMES=1` logs how evenly the frames share the mouse in mouselook (each frame's turn: mean, least, most, the frames off the mean by a quarter or more) and the longest gap between the display thread's event reads. `FREEFALL_ML_TEST=<counts>` moves the mouse that many counts a millisecond from a thread of its own while mouselook has it (no window focus needed), and `FREEFALL_VSYNC_BLOCK=1` makes a hidden window's present wait for its refresh as a full screen's flip does, so both can be measured headless (`FREEFALL_HIDDEN=1`). Example, a Random Scenario turning for 12 s: `FREEFALL_HIDDEN=1 FREEFALL_WINDOW=2560x1440 FREEFALL_VSYNC_BLOCK=1 FREEFALL_ML_TEST=2 FREEFALL_ML_TIMES=1 FREEFALL_SCRIPT="<the random scenario script above>;+12000:q"`.
- With `SDL_VIDEO_DRIVER=offscreen SDL_AUDIO_DRIVER=dummy` the Linux build runs headless; the Windows build runs under Wine with `xvfb-run`.

## Frame-by-frame comparison with the original (step 4)

`verify/port_compare.py` runs the original `__FF.EXE` in the emulator (`verify/frame.py`) and the 32-bit Linux build of `tnfree` side by side, with the same input, and compares them frame by frame: the screen, the palette, the original's whole data object and (every few frames) every heap block.

For that `tnfree` has a **lockstep mode** (`port/test/lockstep.c`, turned on by `FREEFALL_LOCKSTEP=<dump file>`). It makes the port see exactly what the emulated original sees:
- a fixed clock: the Miles timers never fire, the game's 250 Hz clock advances by 0x32 at the start of every frame, and the frame limiter in `GameTimeFrame` ends at once;
- scripted input only: keys go into the keyboard handler's buffer and the mouse into the driver at the frame the script names (`FREEFALL_LOCKSTEP_INPUT`); window input is ignored (a mouselook move can be scripted too: `L<turn>,<look>` in angle units, 0x10000 a full turn);
- the VGA status port and the PIT counter read like the emulator's;
- no movies (the emulator has no DOS file access for them);
- fresh heap blocks filled with `CD` bytes and freed ones with `DD`, like the emulator's heap (Linux build; `CMakeLists.txt` wraps `malloc`);
- the original's big heap blocks at the same address modulo 64 KB (`FREEFALL_LOCKSTEP_ALIGN`, filled in by `port_compare.py`), because the original stores the low halves of some pointers (see the report).

At every frame it appends the state to the dump file, and writes `<dump>.map` with the address ranges and the routine table the comparison needs to tell pointers apart: a pointer into the data object, to a routine, into the screen, the stack or a heap block is equal when it points to the same place on both sides (heap blocks are paired per frame).

```sh
cmake -B build-lin -DCMAKE_TOOLCHAIN_FILE=cmake/linux-i386.cmake -DSDL_UNIX_CONSOLE_BUILD=ON && cmake --build build-lin
cd verify
# mission 1 started directly (the decompilation's snapshot), default input
python3 port_compare.py --port ../build-lin/tnfree -n 600
# the real way in: menu, New Game (Skip), base, briefing, Outfit Complete, then play
python3 port_compare.py --port ../build-lin/tnfree --mission 0 -n 1000 --input "$(cat inputs/m1-shell.txt)"
# plan an input script: run only the port and save its screen every 40 frames
python3 port_compare.py --port ../build-lin/tnfree --mission 0 -n 1000 --scout --shots 40 --input "..."
```

Input script: `frame:action;...` with `d<scan>` / `u<scan>` (key down / up, set-1 scan code in hex), `t<scan>` (both), `m<x>,<y>` (mouse in driver units, 8 per pixel in 640x480), `b<buttons>`. The game's movement keys are W / X (forward / back), A / D (turn), Z / C (strafe); the arrow keys look around.

Some data differs on purpose: the private state of the code the port replaces (DOS, the C runtime, Miles, Smacker, the video, keyboard and mouse drivers). Those ranges are listed, each with the reason, in `EXPECTED` in `port_compare.py`; the game's own code never reads them.

What the comparison found and fixed is in `docs/decompilation/frame-comparison.md`.

## Options that must not change the game (`verify/state_compare.py`)

An option that changes only the picture (screen filters, 3D resolution, widescreen) has to leave the game exactly as it is. To check one, run the same mission with the same input twice in lockstep mode, once with the option off and once on, and compare the two dumps:

```sh
# u-off / u-on4: user folders with tnfree.ini holding screen_sharp3d=0 / screen_sharp3d=4
FREEFALL_LOCKSTEP=off.dump FREEFALL_LOCKSTEP_FRAMES=150 FREEFALL_LOCKSTEP_HEAP=25 setarch -R build-lin/tnfree --user u-off ...
FREEFALL_LOCKSTEP=on4.dump FREEFALL_LOCKSTEP_FRAMES=150 FREEFALL_LOCKSTEP_HEAP=25 setarch -R build-lin/tnfree --user u-on4 ...
python3 verify/state_compare.py off.dump on4.dump --all --ignore-block 209ae048
```

For this the two runs must lay out the heap the same way: in lockstep mode the game thread gets its own deterministic heap (`port/test/lockstep.c`: blocks of power-of-two sizes from a fixed address, 0x20000000), `setarch -R` turns off address randomisation, and the paths (user folder, dump file) must have the same length. Blocks of other threads (sound, display) are left out. The config table block (G8: bytes the original never writes) differs from run to run and is skipped with `--ignore-block`. Runs with the same settings still fall into a few heap layouts now and then (from the first frames: a race between threads at start-up, not yet found), so when two runs differ from frame 2 on, make a few more of each and compare the ones that match at the start.

## 3D resolution (`port/video/sharp3d.c`, called "3D sharpness" before)

The game draws its frame as before: its 3D view, then the HUD over it, so the object under the pointer, the AI's "seen" marks and the pitch limit come from the original picture. Right after the game's 3D view (`hud_269028`), `port_s3d_render` draws the same view again, `kx` x `ky` times bigger:
- the whole data object, the camera list block, the 3D point pool and the block of the 4 ground textures with blast marks (`blasttm.c`: the data's table says which copy holds which texture; without it the sharp drawing's refills left the game's marks on the wrong squares, P71) are saved before and put back after, with interrupts held meanwhile;
- the render stack, the save canvas and the tables with one entry per column or row are swapped for bigger static ones (`port_s3d_on`; the macros at the end of `g5_b.h` / `g5_c.h`);
- the camera is a copy with the bigger canvas, so the view is the same; when `kx` != `ky` the aspect is changed so the vertical zoom stays;
- what the game draws at a fixed pixel size is drawn `k` times bigger there: rain and snow (`weather.c`), particle pixels and discs (`particle.c`, `rndsky.c`), sun and moons (`rndsky_2A80FC`), stars (`src/3d/star.c`), 3D lines and their limits (`drawobj.c`); the sky spans are cut into pieces of 255 pixels (the span asm counts in a byte), and the cloud rows' directions are worked out per row instead of stepped (the steps' rounding adds up over many rows: P20).
- two sky loops that go down the canvas's columns, the plain sky fill (`rndsky_2A82D0`) and the water reflection (`rndsky_2A8658`), go a row (or a band of 64 rows) at a time across all the columns instead: a column of the goggles' tall view in a tall window is too long for the CPU cache, so each pixel was a cache miss (a cache simulation showed 6 times as many misses per instruction as the cockpit's). The same pixels come out (checked on every reflection of 230 frames in missions 1 and 7). The reflection skips a band of rows, and in a band the groups of four columns, where no pixel has a water colour (a four-bytes-at-a-time test), and the sky fill writes whole rows above the land with one `memset`.
- the clouds' distance steps blend (`rndsky.c`): `rndsky_2A7078` shades each cloud row by its distance in steps (`sky_dist`: the clouds' own colours, 7 tables ever closer to the haze, 3 plain haze colours), and at the sharp view's sizes the rows where the step changes showed as lines across the sky when looking up. Each row keeps where it lies between two steps (`sky_band`: step * 16 + 0..15, the change centred on the game's) and `rndsky_2A7654` draws its span with one step's colour or the next's by a 4x4 dither (`sky_span_dither`).
- the far shores (`haze.c`): the column terrain fills the span between two ring points with one square's texture, so a water or shore square (a texture with water colours, `hz_wtex`) with a corner up on the land filled the slope up to the land with water colours, which Water reflection then showed as sky (G18). `hz_span` splits such a span at the water's height (the lowest of the square's height and the two points'): the water square's texture up to there, the higher point's land square above it, so the outline stays the game's. The points' view positions and squares are kept as `walk_square` goes (`hz_pvy` / `hz_pvz` / `hz_ph` / `hz_pcell`, the last point's as `hz_l*`).
- the flat8 sprite scaler (`src/2d/fl8s.c`, port only) draws the same pixels with one loop per kind and a magnified sprite in runs of pixels per texel: a sprite close to the camera covers millions of pixels at 6x (P31).
- the perspective mapper's scan (`gri_per_scan`, `src/2d/perscan.c`) works out each run's texture steps with the plane's terms times the run's length; the game keeps the terms under 0x200000, which fits 32 bits for runs up to 1024 pixels only, so the sums are 64-bit in the port (rows that fitted give the same values; a wrapped sum smeared a near roof's texture below a line across the screen, P129).

When `GfxBlit` copies the view to the screen, the picture goes to the display (three buffers) with a copy of the view as the game copied it to the screen (`scr`), and the display shows the sharp picture wherever that copy still holds the game's 3D pixels and the copy where the HUD drew over them, the screen itself under the pointer (which the game draws onto the screen later). Comparing with the screen as the display finds it was wrong: the game may already have copied its next frame there (P17) (`platform.c`, `sharp3d_compose`; `FREEFALL_S3D_NOMASK=1` shows only the sharp picture). The cost is about 1 ms a frame at 2x, 3 ms at 4x and 7 ms at 6x (one core); `FREEFALL_S3D_TIME=1` writes the main view's drawing time to the log every 100 frames.

The target's label (`hud_target_label` in `hudmain.c` -> `port_label_piece`, `sharp_label`): with a sharp picture of `kx` and `ky` 2 or more, the label's text (font 0x1F7: the name, the distance, "Locked" / "Out of range") is drawn as the game draws it on a canvas of its own (the text with the canvas's colour and fill, and a mask of the pixels it sets), then laid into the main view's sharp picture at 3/4 of the game's size (`LABEL_Q`; half the size in earlier test builds, too small to read), each picture pixel taking the text pixel under it (rows of 2.25 pixels at 6x in 320x400 alternate 2 and 3). Each piece is placed by a point of its box (`ax`, `ay`: 0 left or top, 1 the middle, 2 right or bottom), so pieces line up at any size. The game's own text still goes onto its screen; the same pixels are written into the view's `low` copy (the 3D before the HUD), within the canvas's clip, so the display counts them as the 3D's and shows the sharp picture there. On the wide view's layer (`port_s3d_hud_begin`) the game's text is not drawn at all. At 2x in 320x400 (`ky` 1) the label stays the game's.

"Target label: Around the box" (`port_target_label`, ini `target_label=box`; `hud_label_around`): the game makes the label as one string (the name, a blank line, the distance, a blank line, the mark); it is cut at the blank lines into three pieces: the name where the game has it, right of the box; the distance centred above the box (the current target's status ticks, or the brackets of another target), the mark ("Locked", "Out of range") centred under the health bar, each line centred in its piece (`label_text`). At the canvas's top both go under the box, at its bottom both above. A string not in that form is drawn as the game's block. At 3D resolution Original the pieces are the game's letters at the same places.

The maps (`port_s3d_map` in `sharp3d.c`, `port/video/mapsharp.c`): right after the game draws a map (`mapdisp_276EF8`: the squad map `hview3d_272CFC`, the side screens' other maps `hview3d_272E84` / `hview3d_273500`, all as slot 1 + view, and the full map in `hud_map_legend`, slot 0), the map is drawn a second time into the view's picture, with the same save and put-back as the 3D. The map display is a copy with the scale divided by `kx` and `inv` multiplied by it; in 320x400 (`kx` = 2 `ky`) the y shift `hud_35A544` is 0 meanwhile, so a picture pixel is as tall as it is wide. The terrain is drawn for that scale (`mapdisp_2774C0` with `port_map_pass`: `sharp_terrain` gives the same pixels a cell's run at a time, black beyond the land's edges) and kept until the map moves, the game's own terrain bitmap changes or Map smoothing changes. Map smoothing On (`screen_map=on`, `port_map_smooth`; earlier test builds' `smooth` and `soft` are read as On; the option was called Map land, Squares / Smooth; `smooth_terrain` in `mapdisp.c`): each square's values as the game finds them (`map_sq`: its ground kind's colour row `game_41DD58` / `planet_res47` or the mission overlay's colour, its height, and its light from the slope to the next square through `mapd_shade` / `mapd_shade8`) sit at the square's middle; a pixel takes the kind with the most bilinear weight among the four squares around it (so the edges between kinds are smooth curves, an odd square a rounded blob), the height blended from those squares of that kind picks the colour in the row, and the light is blended from all four, rounded, through `planet_light` / `planet_tab36` as the game's. The rows of the two square rows are blended once per picture row (`hv`, `sv`, `kv`), so a pixel with one kind all round takes two multiplications. 6x in the test container: the full map (2376 x 597) 6 to 7 ms when it is drawn again (Off 1.5 to 4), a side screen's map about 1.3 ms (Off 0.5). The blast rings and the view cone (`port/video/mapcone.c`, its radius and edges times `kx`) scale by themselves (the rings' y radius through `grd_cap->aspect`, as for the 3D). What the game draws a pixel at a time goes to `mapsharp.c` while `port_map_kx` > 1 (the `SHARP_OR` calls in `mapdisp.c`): dots as a `kx` x `ky` block, crosses, boxes, lines, the player's heading tick, vehicle outlines and circles half a game pixel thick (circles as the game's pixels show them: an ellipse in 320x400, as there), text and annotation bitmaps drawn on a canvas of their own and laid as blocks, the blast disc through `rndsky.c`'s sharp disc. Every mark is at its exact place: the game's pixels round it, so a text the game puts just above the map can show its bottom rows. The display treats the map's picture like a 3D view's: the map wherever the copied screen still holds the game's map pixels, the screen where the HUD drew over it (the legend, the zoom buttons, the messages). State check: off against 6x, 130 frames of mission 7 with the full map open and closed: no difference. In the cockpit the game redraws the side screens' maps every 75 ms (`hview3d_273CAC`; the goggles' every frame); with the view cone or Frame rate 60 fps they are drawn every frame, and the random stream the contacts' flicker takes (`game_rnd_35B704`, shared with the game's objects) is put back after each extra drawing (`extra_begin` / `extra_end` in `hview3d.c`; P42).

The goggles with their screens hidden (Tab, `hud_35AEF0` bit 0; P105): `helm_gimbal_label` (`helmet.c`) draws the Gimbal mode label at the middle screen's bottom line, and `port_map_hidden` (`mapdisp.c`) the map's view cone (Map view cone), the suit's mark and, with Show enemies without MFD (`port_map_enemies`, ini `enemies_without_mfd`), the map's contacts, at the middle screen's map's place and scale, over the main view (not while the full map is up, `game_camera_38FB20`: it has its own cone, P80). The place is the goggles' own middle screen (`W(48)`, the dropship's `W(61)`: after the goggles came on with their screens hidden the views are still the cockpit's, `helm_263BE4`), from the canvases' places on the game's screen. The map is view 1's (mode 8 `hview3d_272CFC`, mode 9 `hview3d_272E84`, the goggles'), its scroll after the unit it follows worked out the way `mapdisp_276C6C` / `276CDC` would do it, without drawing; with another page there a map as `mapdisp_276ACC` makes one at `hud_map_zoom`. The player is then held at the map's middle (`mapdisp_276BC8`'s middle; the owner's ask after P105: the cone and the suit's mark stand still, where the scroll's steps and the map's pixel steps moved them) and the contacts are placed around it. ## Widescreen (`port/video/sharp3d.c`, option "Widescreen")

In a mission's screen (the cockpit and the full-screen goggles) the main view's sharp canvas is made wider: the screen gets `E` more of the game's columns on each side, `E` worked out by the display from the window (up to 16:9, the owner's choice; `port_s3d_wide_e`), and the main view its share of them (all of them for the goggles' full-width view). The camera is the game's with `half_w` set to the wide canvas and `zoom` lowered by `w / (w + 2E)`, so a unit is as many pixels as in the game's view and only the sides are added ("Hor+"); `zoom_y`, the bands and the distances stay. `fov_x` stays too: the objects' view distances scale with it (`viewdist_2A0E14`: a wider angle makes them vanish nearer). The game's 4:3 picture and HUD are untouched; the display stretches the screen and lays the wide picture behind it (below). Rain is repeated one view width out on both sides. With a 3D resolution where `kx` != `ky` (the 320x400 screen) the aspect is set again before each side's second drawing (below): the game's drawing puts it back, and with the game's aspect models were projected at half their distance from the middle there, judged hidden by the land (`viewdist_2A2284`) and cut at the seam.

The mouse beside the screen (over the wide view's sides): the display works out the pointer's real position (`to_game`, `port_wide_ptr` / `_x` / `_y` in `sharp3d.h`) and hands the game the screen's edge, so the game's own pointer and hit tests stay in their 320 columns. The HUD then takes the real position where it matters: `helm_2623E4` gives the main view the event at that position, `hud_aim_point` aims there (the projection in `viewdist_2A28D0` is plain arithmetic and reaches past the view), `hud_269F28` picks the unit for a right click among the boxes the wide view drew (`hud_26A11C` records them while it draws: `port_wide_target`), `hud_aim_on_target` uses that box for the current target, and the probe pixel is off. The game does not draw its pointer meanwhile (`cursor_save_under`); the display draws it. With the pointer on the screen nothing of this runs: the state check with the option on matches the run with it off. Replays do not record the position beside the screen.

The terrain builder (`terrstrp.c`) walks three 45 degree sectors around the heading, which reach at least 45 degrees on each side (the game's view) and more toward the middle of a sector. In the wide view the cone reaches on each side as far as the picture or the sectors do (`port_ts_room`; two set-ups of the strip record, one edge from each). Where a side falls short, the builder runs again with the sectors turned 22.5 degrees that way (`port_s3d_ts_turn`, only the choice of squares turns) and adds the squares and vertices the main run did not make after the main ones (`ts_mark` / `ts_extra`: marks per square and per vertex cell, by generation); then all the squares are put in ring order again, a stable merge that keeps the main squares' own order (`TerrainStripBuild` at the end of `terrstrp.c`; the strip record stays the main run's). So the wide view is drawn once. Before, the whole view was drawn again for each such side and only its outer columns kept, which made a frame cost up to twice as much depending on the heading (the goggles' fps jumped as you turned). The picture is the same as with the two drawings except a few pixels near the old seam (checked frame by frame in missions 1, 7, 10, 29 and 30). The terrain buffers (strip pool, vertices, clipping points) are 4 times as big while the sharp view draws; a run that would fill the pool or the vertex buffer stops there.

The stretched screen (`port_s3d_stretch`, set by `hud_269028` in a mission, cleared by `helm_261A00`; not while the game's options screen is up): the display stretches the whole screen evenly to `w + 2E` columns, and the main view, `fw` columns wide, gets `fe = fw * E / w` more on each side, so its picture is exactly as wide as the stretched view rectangle and keeps the game's proportions. The game's own picture sits in its middle at its own scale, which keeps what the HUD draws over the 3D (reticle, brackets, nav marks) on its units. `ck_compose` (`platform.c`) lays the wide picture over the stretched screen where the view's window is (the shape is worked out in `win_shape` only when the widget, the art or the view's place change): the main view widget's stencil (`port_s3d_window`, the shape the game uses for mouse hits), minus the art the game draws over the view each frame (the cockpit's frame piece, resource 0x2F00000, or the goggles' helmet, 0x2EF0000: `helm_draw_frame` hands its mask and place to `port_s3d_overlay`). The stencil's rows are coarser than the art in the 320x400 screen, so up to three pixels beside it that no art covers are window too (`win` = 2) where the copied screen still shows the 3D there (P18). A popup help box (`helm_263940` hands its rectangle to `port_s3d_tip`) is shown whole with the stretched screen (P19). The stretched screen and the window are sampled with the same column rule (the screen's texture nearest), so their edges meet exactly. There the pixel is the wide picture's, or the HUD's where the game's screen differs from its 3D at the same place of the game's picture. The mouse follows the same geometry (`to_game`): over the cockpit the stretched screen's pixel, in the window the game's picture's pixel, and beyond the game's picture the side pointer (`port_wide_ptr`, as with the goggles). The display draws the pointer itself (`port_wide_cursor`, `cursor_save_under` draws none). The side screens' views are stretched with the cockpit. In the goggles they sit inside the main view: there `ck_compose` takes each side screen's sharp picture (the game's screen where the HUD drew over it), not the game's screen (P24).

The maps in widescreen (`port_s3d_map`): the full map gets the main view's extra columns and window shape, so `ck_compose` lays it like the wide 3D (the map display stays where the game keeps it). Its zoom stops where those columns would reach past the land (`port_map_zoom_ok`, `wide_scale` in `mapdisp.c`, from `port_map_extra`): the farthest zoom's scale is lowered so the land's 512 squares fill the wide map exactly, a zoom that would show no more than the next one is skipped (`hud_26AFB0`, the side screens' zoom buttons, and when the map opens, `hud_26AE98`), and the scroll and the clamp to the land count the extra columns (`mapdisp_276CDC`, `mapdisp_2779A0`), so no black shows beside the land. The cockpit's side screens are stretched with the screen, so a side screen's map gets its share of the extra columns too (`ex`; the goggles' side screens sit inside the main view and are not stretched) and `ck_compose` lays it over its stretched screen with the picture's columns 1:1, centred, the stretched screen wherever the HUD drew over the map (the zoom buttons and the text stay with the cockpit). The mouse there (`to_game`, `ckm_at`): the map picture's column; beyond the game's map the game gets the pointer at the map's edge and the real column in `port_wide_map_x` (`port_wide_map`: the slot), which the squad map's click (`hview3d_272A48`) uses for the order instead of the zoom buttons at the edge; the full map's clicks beside the game's picture come through `port_wide_ptr` like the 3D's, kept on the land (`hud_map_mouse`). The display draws the pointer at the real place (`ck_col`).

The targets' overlay (`hud_26A188`: the brackets of the other targets, the current target's status ticks, name, distance and LOCKED) is drawn on a layer as wide as the wide picture (`port_s3d_hud_begin` / `_end`, 8 bits, 0 = nothing; part of the frame it was drawn with) instead of the game's screen, so it is whole on units the game's 4:3 view cuts or does not see, and none of it lands on the cockpit's art at a stretched place. `hud_targets_wide` changes the game's values exactly as `hud_26A188` does (the same calls on the game's target list, the same `drawobj_29CBA4` and sound); the places come from the wide view, which records each unit's box and point while it draws (`port_wide_target`; the point is `drawobj_29CBA4` without its clamp to the canvas, `port_hud_noclamp`). A label the game itself would not draw (its unit is outside the 4:3 view) uses its own dice for the garbled name, not the game's random stream. `ck_compose` puts the layer over everything in the view's rectangle, as the game's overlay is drawn over the cockpit's frame there.

State check: with the option on, every game value matches the run with it off (300 frames of mission 1 with turning, pointer moves, firing and a right-click target, in the cockpit and in the goggles; 3D resolution 2x and Match window). The only differences are two short heap blocks on one side for one frame (the cockpit, frame 2).

## Anti-aliasing (`port/video/shaders/fxaa.frag.hlsl`, `port/video/screen.c`, option "Anti-aliasing")

Off or FXAA (`screen_aa=fxaa`), on the GPU renderer only (the shader filters' Direct3D 12 / Vulkan path; "not available" without it), with 3D resolution 2x or more. A point-sampled FXAA pass (after FXAA 3.11's quality version: the edge through the pixel from its 3x3's luma, followed both ways in 10 steps of 1 to 8 pixels to its ends, the pixel blended with its neighbour across the edge by how far it is from the nearer end, and small details by the local contrast) runs on the composed picture before it is scaled to the window (`port_screen_fxaa`), so it works on the sharp picture's own pixels. The target's sharp label (`sharp_label` in `sharp3d.c`) is kept out: each label notes its box and which of its pixels are text (`port_s3d_frame.lab`, a mask in one of three pools), and `label_alpha` in `platform.c` gives those pixels alpha 255, which FXAA leaves alone like the HUD. The display gives the 3D's pixels alpha 254 (`disp3d` in `platform.c`, the palette with the top byte 0xFE) and the HUD, the maps (a frame flag, `port_s3d_frame.map`), the cockpit art and the pointer 255 or 0; the shader changes only pixels of alpha 254, and a neighbour that is not the 3D's counts as the pixel itself, so the HUD's text and lines stay crisp and don't bleed into the 3D. The cockpit view goes over the stretched screen with a blend that keeps the alpha. The shader is compiled to SPIR-V and DXIL and kept as headers (`fxaa.spv.h`, `fxaa.dxil.h`) as the other filters. Switching it on or off makes a new renderer, which also freed the side screens' map textures too late (P48).

Turning a screen filter or Anti-aliasing on or off (a preset can do it) makes the renderer again (`make_renderer`, `port/core/platform.c`): every texture of the old one must be let go of and its pointer cleared there, as SDL frees them with the renderer and a texture of the new one can get a freed one's address (the layered helmet's were kept: P130). Each module that keeps textures has a `*_renderer_gone` call for it; a cache keyed on the renderer compares `renderer_gen`, not the renderer's address.

## Terrain distance (`port/video/sharp3d.c`, option "Terrain distance", called "Terrain detail" before)

Original (the game's; called Low before, `screen_terrain=low` is still read), Medium or High, on the Distance page (on the Terrain & Water page, and the Graphics page before it, in earlier test builds). It changes only the sharp view's camera; with it on, the sharp view is drawn even at 3D resolution Original without Widescreen (at the game's size, for the main view only).

The game's camera splits the land into six distance bands (`FfCamera.band`, `band0`, `band_end`): the bands before `band0` are smooth polygons (`terrrast.c` / `terrstrp.c`), the later ones flat columns (`haze.c`). The game's values are 2 / 12 smooth and 30 / 64 / 100 / 240 columns, steps 1 / 2 / 4 / 8. `detail_camera` sets Medium to 2 / 32 smooth and 48 / 96 / 140 / 240, High to 2 / 48 and 64 / 128 / 180 / 280, before `FfCameraSetup` scales them by the zoom; `detail_clamp` keeps the smooth ring within 48 squares after it (the texture cache `tcache_tab` has 50 rings). Each band's drawing mode is the byte before its record (`ff_cam` +0x5C + 12k; the polygon routine for the smooth bands, 0 for columns): the main view's camera has two smooth bands (modes 1, 2), the side screens' one (mode 2, `band0` 1), so `detail_camera` sets the modes with the bands, the camera's smooth modes on the two smooth bands and its column mode on the rest (P23). For that:
- the terrain vertex grid is keyed by 128 x 128 squares instead of 64 x 64 (`TR_KEY` in `g5_b.h`, `tr_idx` 0x10000 entries; the original key under `TN_WATCOM_ABI`), since 48 squares each way wrap a 64 grid;
- the terrain buffers (strip pool, vertices, `tr_buf30`, clipping points and their limit, `PORT_S3D_MUL`) are 16 times as big with terrain detail on (4 with only Widescreen);
- the haze's bucket list is 0x200 long while the sharp view draws (`haze.c`, `big_head`): far squares reach bucket numbers past the game's 0x80.

Terrain smoothing (its own option, `screen_smooth=on`, `port_far_smooth`; with any Terrain distance, and it turns the sharp view on by itself) draws the far columns textured like the near ground (`haze.c`, `hz_smooth`). The game fills the side of the land between two rings with one square's 256-texel row, a pixel a texel running on down the column (not tied to the land: noise at the sharp view's size, crawling as the view moves), one light level faded only across, and the ring's haze level, so far hills are flat noisy blocks with edges along the squares and the rings. In the sharp view each ring point keeps its place on the map, its light (its own shade) and haze (the game's curve, unrounded), and its ring's line is kept per column (`hz_line`, `hz_smooth_record`, also where it is hidden). A pixel between this ring's line and the last one's (a run, `HzRun`, from `hz_smooth_span`) gets its place on the map between the four points around it, and the texel there of its square's texture: the near ground's 64 x 64 texture (`planet_tex`, turned by the square's variant bits as `weather_2B12D0` turns it for the polygons; the coarse grid's cell beyond the fine map), from the smaller copy whose texels are about a pixel across the span (`hz_mip`: 32 x 32 .. 1 x 1, each texel the texture colour nearest the average of the four below it plus the error carried on, Floyd-Steinberg, so the copies keep the texture's mean colour; made again when the palette or the textures change, not for the cycling colours 0xFC..0xFE). Its light is between the four points, an 8 x 8 ordered dither choosing between levels, the haze rounded to the nearest level. Water or land: a run whose points are all water or all land is that; in a run with both, the land's height is stepped down the run like the place (`HzVert.h`, `HzLine.ha` / `hb` / `hg`, `HzRun.hg` / `dhg`) and a pixel is water where that height is at most the water's (`HzRun.hw`: the lowest water point's height, plus half a unit), so a square with water colours up a slope (a shore square, G18) takes a land point's texture above the water line and the shoreline follows the land's height. (Before, the four points' water shares chose per pixel; with Water reflection High that left pixels the reflection had already drawn as water marked as land: gaps in the far shores.) The values are stepped a row at a time down a run (`hz_run_draw`, on the drawing threads, `port_parallel`); each pixel belongs to one run. The outline and the column buffer stay exactly the game's (what the view sees of objects does not change). Rings under the smooth polygons are drawn as the game does, except where no polygon covers them: the game's polygon builder (`TerrainStripBuild`, `terrstrp.c`) sweeps the near land in three sectors and leaves out some squares the view sees (with Terrain distance Medium and High a hillside's worth about halfway out showed the game's far columns, blocks between smooth land). Each square given polygons is marked for the drawing (`port_poly_have[y][x]` = `port_poly_gen`, counted up once a drawing), and a near ring's span whose squares on the ring line have no polygon is drawn smooth too (`hz_open`; the ring lines are kept for every ring for that). Not with the game's colour table (`hz_clut`) or the flat dark terrain (`game_35CADC`). The first test build blended a typical colour per point instead (the texel nearest the texture's average, dithered between the points); the owner found it a blurry, untextured mess, so it was replaced. 6x in the test container, mission 10: 3D drawing Off 10.0 ms, on 13.2 ms with Terrain distance Medium (10.4 / 14.9 with High).

The near ground's light (`weather.c`, `draw_tri`, with Terrain smoothing in the sharp view): the game lights the polygons with its lit mappers (`gri_lit_per_loop` in `perloop.c`, `gri_lit_lin_loop` in `fl8lin.c`), the light level 0..15 the whole part of a value stepped across the triangle (each vertex 15 - 2 x its shade, plus a half), so a slope shows bands of one level each. With `port_lit_dither` set the level is the value plus an 8 x 8 ordered dither threshold, less a half (`port_dith`, indexed by the pixel's place on the canvas, x in bits 0..2 and y in bits 4..6 so that one add and a mask step both along the mapper's diagonal lines), through a clamp table (`port_dith_row`); the texels and steps stay the mappers' own (`lit_loop_dither`). The shortcut that draws a triangle with nearly equal light as one level (`gri_lit_clut`) is off meanwhile. 6x in the test container, mission 10: about 1 ms more with Terrain distance Medium, 2 with High.

The smooth land reaches into the haze, so each square is drawn through the light table of its haze level (`weather.c`, `bin_haze` / `draw_tri`): the level from the square's distance with the game's own haze curve (`hviewdiv_2AB3CC` with the camera's haze value), the table `planet_light` through that level's `planet_shade` row (`haze_tables`), and the square's objects hazed the same (`hz_level`).

Resources: the sharp view draws objects the game's view does not (more terrain detail, the wide sides), so it may load a resource the game has not loaded, and each `RefGet` moves its resource to the LRU chain's tail. Both would leave the game's heap and its paging order changed. While the sharp view draws, `Malloc` takes memory from its own arena (`arena_malloc`, set in `enter_scratch`): a resource it loads stays there and is taken out of the game's table afterwards, and put back in for the next sharp view while the game has not loaded it itself (`lru_keep` / `lru_back`); the LRU chain is put back as it was. The bitmap headers inside resources that are already loaded get their bits pointers set when first drawn (the same value the game writes when it draws them), which is the only difference left in the state check.

State check (mission 7, 160 frames, and mission 29, 300 frames with jumping and looking down; High with Widescreen against Original): no difference in the data object; in mission 29 those bitmap headers in a few resources. The drawing time at 6x with Widescreen (mission 7 / 10): Low 5-6 ms, Medium 6-7 ms, High 7-9 ms.

The display (`platform.c`) fills the sharp picture's texture only for a new picture (`port_s3d_frame.serial`, the pointer's rectangle and the palette unchanged: `s3d_made`, `ck_made`); the game makes 25 or 60 pictures a second and the display shows each refresh. Show FPS (`fps_meter`) is drawn over the finished window, centred at the game's row 44 of 400 (under the bars) or 41 in the goggles (under the compass), from `port_s3d_stretch` and `port_hud_goggles`.

## The land past the map's edge (`port/video/mapedge.c`, G34, G35)

In every preset (the game's own drawing, the sharp view and Classic alike). The map (`map.c`) has a fine grid, 0x201 x 0x201 cells for the 512 x 512 squares one plays on (`rows2`, a row 0x603 bytes), and a coarse grid, a cell every 4 squares, 257 x 257 for the land around them (`rows1`; the fine area starts at its cell `x0`, `y0` = 64, 64), which the terrain caster's far rings and `map_2949C4` read past the edge. The near ground read the fine grid only and never checked the edge: the strip builder (`terrstrip_2AA2B4`) let the squares at x or y = 512 through, whose far corners `terrrast_2AE004` read one cell past the row (the next row's first cell, the map's other edge) or past the grid (G34, a wall along the east and the south edge), and past every edge the polygons stopped and so did the caster's near rings (its fine walks clip to 0..0x200: `haze_2B4FD0`, `haze_2B50DC`, `haze_2B51AC`, `haze_2B52D0`), so the land there was missing until the far rings began (G35, the far land showing through as a see-through wall).

`port_pf` is a copy of the fine grid with `PF_M` (256) squares of land around it, `PF_W` (0x201 + 512) cells a row, and the near terrain reads that instead (`mapedge.h`: `PF_CELL`, and `PF_IN` / `PF_IN1` for the bounds): the polygons' cell walk (`terrrast_2AE004`, its steps of +-0x201 made +-`PF_W`; a corner past the copy clamped), the polygon routines (`weather.c`, `CELL`), the strip builder's bounds and its marks (`ts_have`, `port_poly_have`, both `PF_W` x `PF_W`), and the caster's fine walks (`hz_on_map`, `hz_sq`, `haze_2B3FD0`, `haze_2B40C8`, the clips' `FLO` / `FHI`, `hz_stride`). The land around is the coarse grid's, at every square as `map_2949C4` has it there (each coarse cell split into two triangles by the parity of its place); its lattice points on the map's edge are the fine grid's own cells, so the land goes on from the edge without a step (the coarse cells there are not the fine grid's). A cell's shade is the four points' shade between them the same way (halved and rounded to the fine grid's 0..7, in bits 7..9), its kind the coarse cell's (bits 0..5; bit 6, a blast mark in the fine grid, stays clear), its variant (bits 2..3 of the second byte) a hash of its place. `port_pf_sync` makes the copy of the map again on the first 3D drawing after each game frame (`port_pf_frame` from `port_frame_limit`; blast marks change the map), about 0.8 MB, and the land around only when a hash of the coarse grid, the map's place and the fine grid's edge cells changes (a new map); about 0.1 ms a frame in all. The squares off the map have no tile objects: `viewdist_2A13B8` looks them up only on the map (a square at 512 read its 4 x 4 group from past `game_3C5E1C`; the first version of this crashed at mission 10's corner reading them for the land around).

Only the picture changes: the game's heights, physics and AI read the map itself (state check, mission 9 looking at the east edge, 120 frames: every unit's place the same). AddressSanitizer runs clean at the four corners and the middle of the east and south edges in missions 3, 7 and 10, Freefall and Classic. The benchmark (`--bench`, Freefall at 1920 x 1080) is the same within its noise.

## Object distance (`src/game/render/viewdist.c`, `src/game/terrain/haze.c`, option "Object distance")

Original, Far or Farthest (`screen_objects=far` / `farthest`), on the Distance page under Terrain distance (on the Trees & Objects page, and the Graphics page before it, in earlier test builds), in the sharp view only (`port_s3d_wanted` turns it on, at Original without Widescreen too). The game decides per object whether it is in range (`viewdist_2A0E54`): the Chebyshev distance in squares times `(fov_x + 0x100) >> 11` (4 at the normal zoom, less zoomed in) against 4 times its class and type's entry of `vd_dist_tab` (resources 0x560..0x568: soldiers 20, most vehicles 30, buildings 40, a few 50 to 80). Far doubles that, Farthest makes it 4 times, except for whatever of the enemy can shoot (`vd_enemy`, the owner's call: nothing of theirs seen earlier than in the game unless asked for): an entity of classes 1 to 3 whose brain (`f21`) is on side 2, as in the game's own enemy checks (the player's side is 1), and the class 5 shots whose owner (record +6) is one of those follow "Enemy distance" instead (`screen_enemies=far`, `port_enemy_dist`: twice the game's distance, also with Object distance at Original); class 4 on side 2 with a weapon in its record (+0x33, the gun turrets, types 0x45..0x47 in the missions) always stays at the game's distance. Past that the game has more limits, lifted in the sharp view while either option is on:
- The caster collects moving objects (the grid's cell lists, `haze_2B3BA4`) only out to ring 0x78, 120 squares (`HZ_OBJ_RING`: the whole map), and parks those beside the ring in buckets that are drained only below `hz_nheads` (the third band: here all 0x200).
- Parked objects take nodes from a pool of 63 (`hz_nodes`); the sharp view has its own of 0x140, every entity, set up for each drawing.
- Tile objects (trees, rocks: `tile_groups` stamped on 4 x 4 squares) are collected only on squares the caster walks while its ring is within `dist[4]` (20 squares, `walk_square` -> `haze_2B44FC`) and on the polygons' strips (`weather_2B1814`, 12 to 48 squares with Terrain distance). `hz_tile_rings` adds every square of the square rings from there out to 48 (Far) or 96 (Farthest), counted from the viewer's square, each a ring before the caster draws it (as for the moving objects): the square's column from the projection of its middle (`haze_2B4198`'s, without its side effects and with a 64-bit division), then `viewdist_2A13B8` on the viewer's strip with that column's height in the column buffer, so the land drawn nearer hides them.
- The placements of tile groups (`tile_places`, 512 records whose `next` the lookups follow by its low byte: 255 at most) and the tile object ids (1024: `tile_3C9E1C`, `vd_tile_info`) run out at about 50 squares in a forest. While the sharp view draws (`port_s3d_on`), `tile_places` and `tile_3C9E1C` are bigger copies (`g2_a.h`: 0x800 placements, 0x2000 ids; the groups' own records copied in at each drawing's start, `tileobj_299048`), the lookups follow the whole `next`, and `vd_tile_info` is allocated that big.

The far objects take the haze level of the ring they are collected in, as the game's own far objects do. Only the picture changes: the sharp view is drawn on a copy of the game's data (P-series notes above); in a state comparison (mission 2, 130 frames, Original against Farthest) the data object matches in every frame. The game's heap differs in the data of a few loaded 3D models, which the drawing writes into (resources 0x35F..0x36A in mission 2), not read by the game's logic; the game's own picture matches. Mouse targeting uses the game's own drawing (the sharp view has no probe), so a unit only Object distance draws can't be clicked.

## Fog (`port/video/fog.c`, option "Fog")

Off or On (`screen_fog=on`; earlier test builds had Light and Strong, both read as On now), in the sharp view only (`port_s3d_wanted` turns it on for the fog, at Original without Widescreen too). The game's own haze (`planet_shade` rows by distance) never reaches the sky: its last level is a grey-blue per colour, so the old "Distance fog" (the haze nearer) could not hide the far land. Here every colour goes through one more table last, `port_fog_tab[f][c]` (f 0..16): the palette colour nearest to the colour mixed f/16 of the way with the fog colour, made again when the palette, the fog colour or the planet's tables change (the palette's cycling entries, 0xFC..0xFE in the missions, are left out: they changed every five frames). The fog colour is what the sky fills the rows below the horizon with (`rndsky_2A7A6C`): 0xA2 (or 0x20) under the cloud sky, the colour that also ends its haze bands at the horizon, 0 under the stars (night missions), the fill colour without clouds. Past the fog's end the land is not drawn: the caster stops after the first ring past it (`haze_2B5484`), and the sky's fill shows there, the same colour, so the fog also saves the far rings.

The fog follows the true distance on the map from the viewer (`port_fog_at`: by distance squared through a table, from start to end along t²(2 − t), gentler than the smoothstep of earlier test builds: 3/8 fogged half-way, so the land stays clear longer and thickens toward the end; the squared distance in 1/64 squares times a reciprocal made once per view, `fog_mul`, so no division per point (P44)), so it does not move as the head turns as the caster's square rings would. 80 to 240 squares (Strong, taken out, was 40 to 140); in rain or snow (`game_35CADA` not 0xFF, part of the table's key) the start times 0.55 and the end times 0.7, so the fog is nearer and thicker; times the zoom's scale of the camera's bands (`port_fog_view`, from the last band as `FfCameraSetup` scaled it). Where it applies:
- the caster's columns (`haze.c`): each ring point's fog (`hz_lf`, `hz_pf`), the columns of a span between them interpolated (`port_fog_f`), drawn by `colras.c` through the ring's haze row of the column's level and the next one, dithered per pixel (`port_fog_rows`, `port_fog_dd`; a column with one level goes through its table without the dither); the smooth far land of Terrain smoothing carries the fog per point and between the ring lines like its light (`HzVert.f`, `HzLine.f`, `HzRun.ft` / `df`, a fourth dither);
- the smooth ground per square, by its middle (`weather.c`, `draw_tri`: its haze level's table through the fog, `port_fog_ltab`);
- the objects per object (`viewdist_2A2284`: its light table through the fog, `obj_fog`), at most level 12 of 16, so a unit in the fog still shows. The moving objects the rings past the fog's end would have collected, out to the game's 120 squares (`0x78`), are still collected at the end (`hz_fog_objects`), so units past the land's end are still drawn;
- the water, after the reflections (`port_fog_water`, `rndsky.c`, from `ffpipe.c`): each water pixel of the land by where its ray meets the water (the water's height from `water_level` walked out to the fog's end), the fog every 32 columns of a row and interpolated between, on the drawing threads; a span of 32 with no fog at either end is skipped, and the fog between is stepped, not divided per pixel.

The water passes find the water by its colours (0xA2..0xAF, `sky_water`) and the day fog colour is 0xA2: the tables keep water colours water and the land's colours the land's, 0xA2 counting as the land's while the fog draws (`sky_water[0xA2]` is 0 during the sharp view, put back after), and the water's own 0xA2 takes the next water colour even at fog 0. Not with the flat terrain (`game_35CADC` from 0x10). In the infrared view (the canvas's colour table, `fill_type` 1 with `planet_tab3b`) the fog cannot mix colours, since the picture is drawn in the infrared's ramp (0xB0 hot .. 0xE6 cold): `port_fog_begin` gets the table, takes the infrared colour of the sky's haze above the horizon (the fog colour 0xA2 or 0x20 three steps on, as the haze's rows: the table's entry 0xD7 in missions 3 and 7; the fog colour's own entry, 0xD1, is pink in Sci-fi's thermal colours, and the far land faded into a pink band under the purple sky, P52), draws the haze's last rows in it too (`rndsky_2A7078`), and makes the tables a step along the ramp toward it (`ir_tables`); the far land's columns use them as before (`haze.c` with the camera's table, `hz_clut`, which the fog was off with before: the infrared then showed far land the normal view hides, P49), the smooth ground's squares and the objects go through the infrared table and then the fog's in one table each (`port_fog_clut`, the last 8 kept), and the water keeps its colours (no water passes in the infrared). State check: mission 25, 100 frames with a turn and the goggles, 4x with Widescreen, Terrain High and Water High, Strong against Off: the data object the same in every frame, in the heap only the block that two runs of the same settings differ in too; the game's screen differs in a few frames (the reticle, a few water pixels), as it does between Terrain distance Medium and High without fog. 3D drawing time at 6x with Widescreen (mission 10, test container, 4 threads): Terrain Medium Off 9.0 ms, Light 9.1, Strong 9.7; Terrain High Off 10.5, Light 11.7, Strong 11.4. A fogged column costs about twice the game's per pixel (the dither picks one of two tables per pixel; a table per row of 8, a branch-free pick and a byte-wrapped texel index were tried and came out slower with the 32-bit compiler's few registers), and the far land the fog leaves out is a thin strip at the horizon, so the fog saves no time. (The first measurement, Off 20 / Light 19 / Strong 16, was with the far smoothing on, which the fog cut short.)

## True colour (`port/video/truecol.c`, option "True colour")

Off, On or On + sun glow (`screen_truecolour=on` / `glow`), in the main sharp view (`port_s3d_wanted` turns it on at Original too; not the cockpit's side screens, not in the infrared view). The game draws in 256 colours: the sky fades to the horizon in steps, the clouds are a 256 x 256 texture of a few colours stretched over the sky, and the fog is a palette colour dithered between 16 levels. The picture is still drawn exactly as before (the water's passes, the HUD and the display's mask read the same colours); what changes is what the display shows for the sky and the fogged pixels:

- marks: while the main view is drawn (`port_tc_begin` after `port_fog_begin` in `sharp3d.c`, one plane of 32-bit words per picture of the view) the code that draws sky or fog notes each pixel: kind (fog, sky, fill) << 24 | fog amount << 16 | the colour before the fog << 8 | the colour drawn (`port_tc_mark` in `g5_b.h`), and a flag for its row (`port_tc_row`). The sky's dithered spans (`sky_span_dither`) store the kind as a block; the sky's fills (`rndsky_2A7654` with no texture step, `rndsky_2A82D0`) only with the glow; the fogged columns (`colras_fog_column`: the colour before the fog through `port_fog_row0`, the amount from the column's interpolated fog), the smooth far land (`hz_run_draw`) and the fogged water (`fog_water_part`). The objects are not marked: a pixel drawn over later no longer holds the colour drawn (the low byte), so it is skipped as overdrawn.
- the pass (`port_tc_end`, before `port_fog_end`, on the drawing threads in parts of 16 rows): fog: the palette colour before the fog mixed with the fog colour (`port_fog_colour`) by the exact amount; sky: the clouds again in full colour (`port_tc_sky_row` in `rndsky.c`): each pixel the four texels around its point on a softened copy of the cloud texture (a Gaussian of sigma 1 texel, wrapping, `sky_tc_soft`) mixed, plus a finer layer of the clouds' own light at three times the frequency (`sky_tc_fine`, less as the row nears the haze), then toward the haze by where the row is between its two distance steps (`sky_bandq`, 256ths of a step). The steps themselves are fitted to the game's shade tables: step k as the clouds' colour mixed toward the first haze colour by a weight (`tc_w`, least squares over the texture's colours weighted by their texel counts), the last steps the haze colours themselves; made again when the texture, the palette or the tables change (`sky_tc_prep`). Clouds are worked out every second column and the odd ones averaged; a row past the last step is one colour.
- sun glow (`port_tc_sun`, from `rndsky_2A7A6C`; only by day with a sun, not under the stars or with `game_35CADC`): each pixel's angle from the sun (per column and per row tables from the view's zoom) gives a small bright halo and a wide soft one (Gaussians of 0.045 and 0.2 radians, wider as the sun gets low), and a band along the horizon toward the sun when the sun is low (within 0.5 radians of the horizon), all weaker in rain or snow. The glow is a screen blend toward a warm colour (white at noon, orange when low) plus half a tint. With Fog on the fog colour takes the glow too, so the fog is lighter and warmer toward the sun (sun-side fog) and the land fades into it; without fog the glow stops at the horizon.
- display (`platform.c`): where the frame's plane has a colour (`port_s3d_frame.tc`, rows flagged in `tc_rows`), it is shown through the Filters' brightness, gamma and contrast (a per-channel table, `port_screen_grade_lut`) and colour (saturation), keeping the 3D's alpha (FXAA); elsewhere the game's colour. The target's sharp label and the mirror swap clear or move the plane with the picture.

The planes are allocated outside the game thread's heap (`mmap`, or `malloc` on Windows), so lockstep runs keep their heap. Cost (test container, 4 threads, mission 7, 6x with Widescreen at 1920x1080, Water High): about 44 ms a frame off, 65 with On, 73 with the glow: half for the marks while the view is drawn, half for the pass. State check: mission 7 lake, 300 frames with rain forced, shots into the water and the infrared on and off, Off against On + sun glow with FXAA, Water ripples Lively, Water effects, Infrared Sci-fi and Target label Around the box: the data object the same in every frame but the drawing state that two runs of the same settings differ in too (`tmap_tab`, `gfx_blit_bm`, `g3d_tmap_bm`, `hud_pool`), in the heap the config block (G8), the ini strings of different lengths, and pointers into other threads' memory.

## Water reflection (`src/game/render/rndsky.c`, option "Water reflection")

The option's steps: Low (the game's own reflection), Medium and High, shown as "High (experimental)" (`screen_water=medium` / `high`; `advanced` / `full` from earlier test builds are still read).

The original reflects the sky in the water colours (0xA2..0xAF) of the column terrain only (`rndsky_2A84A4` / `rndsky_2A8658`, called between the far columns and the smooth ground): the rows above the horizon are mirrored at it (row `2 * top - r`, a random shimmer offset per colour), through 16 translucency tables of the sky's colour by rows, and where the mirror row would be above the view the water gets the strongest table (nearly flat). The smooth ground, drawn afterwards, does not reflect at all, so looking down at close water shows none.

"Medium" (sharp view only, so the game's own picture and values stay the original's; `port_s3d_wanted` turns the sharp view on for it): `rndsky_2A8658` does nothing, and once the smooth ground is drawn `port_water_full_pass` (called from `ffpipe.c`) works on every water pixel of the land (below `hview_cols`): above the horizon the flat colour, then the sky the reflected ray meets, with the land mirrored over it while the mirror row is in the view (the drawn sky is not mirrored, so the generated sky has no seam where the mirror leaves the view). That sky is `rndsky_2A7078`'s cloud rows worked out again with the view matrix's height column (`m[1]`, `m[4]`, `m[7]`) negated, which is the mirror of the view in the water plane (`water_full_setup`), three rows at a time for the shimmer. The tables go by the angle below the horizon (16 steps over the angle from the horizon to the bottom of a level view, as the original's ramp in a level view), held at table 11 so the clouds still show, mixed between neighbouring steps by a 4x4 dither so the ramp has no band edges. The tables are made again for Medium and High (`water_full_tables`) with each blend matched to the water colours only: the game's own tables pick from the whole palette and some blends came out as the teal 0xA1, green specks along the clouds' edges. State check: game values identical with it off and on (300 frames of mission 7 by a lake, 6x). About 4 ms more a frame at 6x in a 1920x1080 window looking down at water. Objects that stand higher than the land behind them (`hview_cols`, the land's top in each column) were drawn after the sky (`hviewdiv_2AB750`), and above the land's top the mirror took the sky's reflection, so a wall at the water or a unit against low far hills was cut along their outline, which moves with the view (P60). The sky's rows above the horizon are kept as drawn before those objects (`port_water_sky_keep`, from `ffpipe_29E2D8`, at most up to the horizon's row: the mirror reads no lower), and a mirrored pixel above the land's top that differs from that copy is an object's and is mirrored like the land.

Medium and High have no shimmer offsets: the original moves each water colour's reflection by a random row and column, new every frame, so its reflection jittered, and even fixed offsets broke the mirrored land into specks where the water's colours change (the random draws are still made, so the game's random numbers stay the same). The mirrored land fades into the sky over the top tenth of the view's rows (a 4x4 dither), so land cut by the view's top doesn't end in a line when looking down (owner's choice; drawing hidden rows above the view is a later option). The reflection keeps the clouds out to the last distance step at step 7's shade, where `rndsky_2A7078` turns them into the plain haze colour from step 8, so the far water still shows clouds and ripples.

"High" does all of Medium, but the land over the sky comes from a traced ray instead of the mirror row: Medium's row `2 * top - r` is right only for land far away (a close shore or wall is mirrored with land behind it, and what isn't in the picture, a unit standing on the shore below the view, is never mirrored). A mirror camera under the water was tried first and dropped: the map is a heightfield, and its mirror is solid above the mirrored surface, so the reflection showed walls and filled the water. Instead, for one water pixel in every 2 x 2 game pixels near water (`wt_grid`), the view ray (`water_ray`) meets the water at its height and the reflected ray is walked over the map: the fine grid's heights (copied to floats `wt_h`, split into triangles as `map_2949C4` does), buildings as boxes (coarse cell flag 0x40, at the row the game marks it, then `map_2950A0`) and the coarse grid beyond the fine area (`map_2949C4`). The walk starts at 0.25 squares plus 2% of the distance and grows 3% a step, out to 600 squares, with 5 halvings at the hit; it stops once the ray is above the map's highest point. A table of the highest point per 4, 16 and 64 squares (`wt_blocks`, made again when the heights change) lets the ray cross land below it in one step (about 16 steps a ray instead of 43). The hit is projected into the view with the camera's basis (`wt_camera`), and the view's pixel there, when it isn't water, is the reflection. Every second sample across and down is traced first; one between is traced only where those around it differ (sky against land, or land more than 3 samples apart in the view), else it takes their average (about a quarter of the rays where the water shows sky). Each row's pixels are then interpolated from the samples once (`wt_row`: bilinear when all four hit; no division per pixel). Where one of the four is left out or shows sky, the nearest usable sample decides between sky and land, and the land is carried on from the samples that meet land as a mirror carries it (a pixel one column right shows the land one column right, a pixel one row up the land one row down), weighted by nearness: taking the nearest sample's land for the whole half cell gave flat blocks along far shores, where the top samples are left out (P41). A sample is left out (`WT_BAD`) when its water point is under the land (a pixel by the shore whose ray meets the water's plane behind the land: it started inside the ground and copied the shore, the streaks under far shores in the owner's test); a pixel whose four samples are all left out is left as the land drew it (the water colours of a shore square on a slope, G18: Medium's reflection showed them as sky, holes in far hills). Each sample also keeps how far across the map the land it met is (`wt_gd`), interpolated with it, for the objects below. Land above the view's top fades into the sky as in Medium. Rendering only: it reads the map and the entities, never writes game values. Costs in the (slow) test container, 6x in a 1920x1080 window looking across the lake of mission 7, for the whole water pass: Medium 5.3 ms, Medium + ripples 9.4, High 10.0, High + ripples 11.7 (before the owner's test fixes: High 14.0, High + ripples 17.8). State check (330 frames of mission 7 by the islands, 4x, Low against High with ripples, three runs each): the game's values are the same in every frame but three, where a new effect entity's unused bytes (+0x1B..+0x20) differ: the original code leaves them as whatever was in memory (they held address-like values in another run), and a different drawing path leaves other values there; they are overwritten three frames later.

High's objects (`port_water_frame`, `port_water_obj_begin` / `_end`, `port_water_mirror_done`, called from `ffpipe_29E2D8` and `viewdist_2A2284`) are reflected from their own pixels. The first test builds stood each object in for by an upright cylinder as wide and high as its rectangle, which showed as grey or dark cylinders by wading units, splashes and explosions, and as a dark block for the barge (P37). Now each object the view draws (within 64 squares, its base at most 3 squares above the water, only while the last frames' water pass found water) is caught by the screen around its rectangle before and after it is drawn (a pool of bytes per object: before, after, drawn); a per-pixel map of the last object drawn there gives, for any pixel, the land behind all objects (the "before" of the first object that drew it). A 3D model (resource types 0 and 0xF, the ragdolls and debris plates of class 6) is then drawn once more by the game's own call (`drawobj_29AF98`) from the eye mirrored in the water's plane: the view and unscaled matrices with `m1`, `m5`, `m6` and `m7` negated (the height column reflected in the water's plane, g3's y being up, and the view's columns flipped, so the polygons keep their turn) and `_view_position.y` mirrored about the water; the picture is read back with its columns flipped again (`N - 1 - x`, N the canvas width from `_biasx`). It goes into an offscreen picture blanked with 0xFF (a colour nothing draws), clipped to the region the object's four corners map to (with a margin), and the g3 state (matrices, view position, lights, matrix stack) is saved and put back around it; the interpreter's callbacks are off during the redraw (`sfx_28DC9C` would start effects). A flat sprite (resource type 2: trees, explosions, splashes) is flipped from its own pixels along the upright line through its position, each row at its height mirrored about the water (`wo_height`, `wo_flip`), the columns scaled by the ratio of the distances. Tracers, particles and laser bolts (no resource, or other types) are not reflected. Each reflected pixel is stored per screen pixel with its object's number and colour (`wo_rid`, `wo_rc`; between objects the nearer one wins), and the water pass shows it where the object's nearest side is nearer than the land the reflected ray met (`wt_gd`), through that row's shade table. Where the ray meets land that an object was drawn over, the "before" pixel is used, so a unit standing in front of the shore no longer copies itself into the water. A unit wading in the water (a skeleton, `skel_2F74F0`, which notes its lowest joint in `port_water_low`) has its feet a little above the water, by up to two thirds of the eye's height and more and less with each step; mirrored in the water's plane its reflection began below its feet and jumped as it walked (P61). Its model is mirrored in the plane at that joint while it is up to 0.25 above the water (`WO_FEET1`), back to the water's plane by 0.5 (`WO_FEET2`); other models and sprites use the water's plane. Rendering only: everything goes into port-only buffers, the game's values and its drawing outside the water are unchanged.

The water pass runs on several threads (`port/core/workers.c`: `port_parallel(fn, arg, n)` hands parts 0 .. n - 1 to the game thread and up to 7 workers, one per logical core but one; `FREEFALL_THREADS=n` sets the count, 1 for none; the log says "Drawing threads"). The rows above the horizon (flat colour) go first in parts; the two rows at the horizon are done on the game thread; the rows below run in parts of 16 rows (`WP_ROWS`; 32 before, which left threads waiting where the water fills only part of the view) starting at even rows (the ripple field is made on even rows). A row reads only the rows above the horizon and pixels that aren't water, which no part writes, so the parts don't depend on each other; each thread has its own row buffers and ripple state (`WaterTh`, `WrRow`), and the traced grid runs in two passes of parts (every second sample, then the ones between, which read only the first). The picture is the same with 1 and 4 threads (canvas compared at a fixed frame). Measured in the test container (4 cores, shared with the display's software renderer), 6x in a 1920x1080 window by the lake of mission 7: High + ripples 38 to 18 ms, Medium 14 to 8 ms. The window's thread has a pool of its own (`port_parallel_display`: up to 3 workers at high priority, as the window's thread is since P59): laying a new 3D picture into the window's colours (`ck_rows` for the widescreen view, `s3d_rows` for the others, 16 rows a part) took a refresh or more at 4K on one thread while the game's workers had every core but one; in the test container 13 to 16 ms became 5 to 6 ms (2376 x 597, the same pictures with 1 and 4 threads).

The water's height (`water_level_to`, for the ripples, the effects, High's traced rays and the fog's water) is found each frame by walking the line of sight of water pixels, from the view's bottom up every fourth row at 33 columns, over the map (`map_2949C4`) until it meets the ground: out to 48 squares at 1/16 of a square a step, and for the fog to the fog's end at 1/4. With the water in view farther away no line met it, and every one was walked to its end (up to 380,000 lookups a frame, about 10 ms at 6x; P50). Up a column the lines only get flatter, so once one passes over all the land in reach the column's rows above it are skipped. A point a line meets counts as the water only where the map is level around it (`water_flat`: no point half a square away lower): a line can meet land first, the slope of a hill it skims on the way to far water, and that height made the passes see the eye up to two squares nearer the water, with a band of shallows over the water for the frame (P58); and only where the square's texture has the water's colours: a lone water-coloured pixel on level land (a gap between the near ground's polygons on a pier) met the pier, 1.5 squares above the water, the same flash (P73). After 8 such lines the height found before stays. The smooth far land's runs (`haze.c`, `hz_runs_part`) are drawn in 128 parts (32 before) for the same reason.

### Water ripples (option "Water ripples", with Medium or High)

Four sine waves fixed on the water (wavelengths 0.5 to 1.9 map squares, directions around the mission's wind `game_442441`, periods 1.6 to 3.1 s of `game_time`) and a long swell (6 squares, 5.5 s) that still shows far out tilt the surface. Each tilt e turns the reflected ray by 2e: sideways it moves the sample 2e times the focal length in pixels, along the view it moves the pixel up or down the angle ramp (2e of the ramp's angle, times 2.5 so it shows; tables up to 15). Each row's place on the water comes from the true view ray (`water_ray`: the angles as `ffpipe_29EB64` builds the matrix; the game's heights, `ff_view.z` and `map_2949C4`, are in map squares, checked against a lake's far shore) and the water's height, found each frame by walking the ray of a water pixel near the bottom of the view over the map (`map_2949C4`) until it meets the ground (`water_level`; the last height is kept when no water pixel is found). Note the matrix's order: its first column goes with the map's y and its third with x. The field is made every second column of even rows (`ripple_row`); a wave fades out below 12 pixels per wavelength and is gone at 6, so far water stays smooth. Rings around soldiers in the water (`wr_rings`, once per game frame): every active entity of class 1 within 48 squares that stands in water (the ground under it, `map_2949C4`, at the water's height, and its height within 1.2 squares of it) starts a ring every 1.3 s, or every 0.45 s while it moves (at most 64 rings). A ring spreads at 0.6 squares a second for 2.4 s: a short wave train (wavelength 0.3 squares; a soldier is about 0.6 high, measured from the rectangles drawn) weaker as it grows and ages, added to the waves' tilt at each sample of the field (`wr_ring_tilt`). A blue lake mirroring a blue sky has little contrast to show a tilt, so the ring's slope also makes the water colour a step or two lighter or darker (`wr_lite`/`wr_dark`, the water colours 0xA2..0xAF ordered by brightness, dithered). The rings fade out from 6 to 3 pixels per wavelength (by the pixel's mean size across and along the view), later than the waves since they are few and brief. Each row first lists the rings its line on the water crosses and the field columns where it crosses each (outside the inner edge, where the water is still), and the profile across the ring comes from a table: in the owner's test every ring was worked out at every sample of the field, which made ripples with wading units very slow (64 rings close by: 11.7 ms a frame in the test container, now 4). Rendering only: it reads the map, never writes game values. About 3 ms more a frame at 6x in a 1920x1080 window looking down at water, measured in the test container.

The option is Off or On (`screen_ripples=on`). A test build also had Lively (two layers of value noise drifting with the wind set how high half of the waves were from place to place); the owner dropped it, and `calm` / `lively` from those builds are read as On.

### Water effects (option "Water effects", with Medium or High)

Drawing only, with none of the game's random numbers, nothing the game reads (`screen_waterfx=on`):
- splashes (`wr_splash`): a weapon's hit on the water (`port_water_hit`, called from `ordnance.c` with the effect it makes there: a shot's blue sparks, a shell's brown sparks, the big blasts of missiles and grenades, each a size), a soldier or a body (class 1) dropping into the water or gone while it stood in it (`wr_effects`, which tracks the entities from frame to frame); two rings, white foam spreading in the first (the ring pass's colour step, `wr_ring_px`), and the spray (`ws_spray`): drops thrown up from the middle and falling back (gravity 3.3 squares a second², a soldier is about 0.6 high), projected through the eye's axes, white and later the next water colour down, hidden where land on the way rises above the line from the eye to the splash's middle (`ws_seen`: the map's heights every quarter of a square; the screen's pixel there is often the hit's own sparks, P118); at most 16 splashes;
- wakes: a vehicle (class 2) moving on the water leaves a V of rings, one every tenth of a second;
- no rain rings: an earlier test build had them (`game_35CADA` 0), but it rains only in missions on planets whose header's first byte (`game_41DE34`) is not 0, and there `ffpipe_sky_on` keeps all the water passes off (the game draws that water without the sky), so they never showed;
- shallows (`port_water_after`, after the water and its fog, from `ffpipe.c`): each map corner's distance to the land (a corner above the water, or by a square whose texture is mostly land), a chamfer distance of at most 8 squares made once per mission (`ws_field`); within a band of the shore the water colours go up to 6 steps of 13 % toward a light blue (170, 212, 232) (`ws_tables`: the nearest of the water's own colours 0xA2..0xAF and the two light blues by them, 0x93 and 0x95; earlier test builds took 0xA0 / 0xA1 too, a teal green, and then 2 squares and 4 steps of 12 % toward (150, 200, 228), which the owner found too faint). The band is a square wide (`WS_BAND0`) on rows up to 12 squares from the eye and widens to 3 squares (`WS_BAND`) at 64 (`ws_part`, by the distance of the row's middle on the water): 3 squares near the eye looked like a halo around the shores, piers and boats (owner's test). How strong the shallows are follows the size of their water (`ws_amp`): each body of water (its corners, side by side) by its farthest corner from the land, none where that is a square away (a pond) and full from 4 squares, so a small lake is not all light; the shore's corners, counted as land, take their water's strength two corners out, so the band has no edge where the shore's texture is drawn as water. The step fades out toward the band's outer edge and is dithered, and fades with distance from the eye across the rows: full while a pixel covers at most half a square, none from 1.5 squares.
The rings share the ripples' list (192 at most).

## Effects pack (`port/mods/fxpack.c`, `port/mods/effects.c`, option "Effects pack")

A mod's `Effects` folder (`Mods/<mod>.zip`; `screen_effects=<mod>`, `port_fx_pack`; guide for pack makers: docs/modding/EFFECT-PACKS.md), in the sharp view only (`port_s3d_wanted` turns it on, at 3D resolution Original too: the main view at the game's size). The game's effects are class 6 entities whose record keeps an `ActAnim` (`t2_b.h`) at +6; its frames resource (type 2: the effect animations are 1165..1193, the fireball of every death 1171, 15 frames of 71 ms) holds one RSD8 bitmap per item. `drawobj_29AF98` locks the frame the animation shows (`ref`) and draws it with `drawobj_29BE78`, which sizes a sprite by its width in the world (`d->scale`) and keeps the bitmap's proportions, the anchor (the shorts at +0x10 / +0x12) scaled by the same factor. With a pack, `port_fx_frame` fills a frame header of its own (0x1C bytes) with the pack's picture as a FLAT8 bitmap (TLUC8 for the see-through animations, `BMF_TRANS` set) and the game frame's anchor scaled to the picture's size, and `drawobj_29BE78` draws that as it draws the game's frames (it unpacks RSD8 to FLAT8 for its scalers anyway). Animations a pack has no folder for, and the game's own drawing, stay as they are.

- Loading (`fxpack.c`): up to 64 animation folders, each named by its resource number first (`1171`, `1171-fireball`), with up to 240 PNG pictures in the order of their names (stb_image, decoded to RGBA, up to 1024 per side). The folders are listed one level at a time (`SDL_EnumerateDirectory`; `SDL_GlobDirectory` goes into the subfolders too, which the music pack list did, P47). A changed pack is loaded at the start of the next sharp drawing (`port_fx_update`, from `port_s3d_render`) on a thread of its own while the game thread waits, so the options screen and the drawing never meet halfway, and the pictures' memory stays out of the lockstep runs' deterministic heap, which takes every allocation of the game thread.
- Colours (`effects.c`): each picture is turned into the palette in use when first drawn and again after the palette changes (a key over `grd_bpal` 1..0xF7, so the cycling colours 0xF8..0xFF don't remake it): the nearest of colours 1..0xF7 (red, green and blue weighted 2, 4 and 3), looked up once per colour through a 4096-entry cache; alpha under 16 is transparent (0).
- See-through pixels (`port_fx_blit`, called by `drawobj_29BE78` in the sharp view for a pack's picture): the game's scalers draw a pixel or not, so the picture is drawn here, each pixel by its alpha: 240 and more solid, under 16 not at all, between mixed with the canvas pixel behind it in RGB and turned into the nearest palette colour by CIE Lab distance (`mix_colour`, a 32 x 32 x 32 cube filled as colours are met, cleared when the palette changes; Lab rather than weighted RGB, since thin grey smoke otherwise came out greenish). The game's see-through animations (TLUC8, 1185..1187) draw a pack's pictures this way with no translucency table. In the infrared view a see-through pixel is a step along the ramp from the colour behind toward its own, or the nearer of the two off the ramp.
- Timing: the picture is chosen by the frame shown and the time into it, `(item + f) * n / ResNumRefs`, so any count of pictures is spread over the animation's time. f is measured from the animations' last run, `last_time - (next_time - frame_time)` over `frame_time`: the game draws after its clock has moved on by about a frame, which by the drawing's clock put f near 0.7 in every frame and skipped every other picture of a pack with twice the frames.
- Deaths by what died: every death's effect is the fireball 1171 (effect type 0x17, `sfx_28C300` builds it in `sfx_dyn`). When `sfx_28C714` has made it (`sfx_28D0F4` gave the slot), `fx_death` (`sfx.c`) passes `port_fx_death` the slot, its animation, the class, and for class 0 its living model (`drawobj_cls0_models`) and width (`ff_image_model_width`), for class 4 whether it has a gun (`game_cls4[slot][0x33]`); `sfx_28D0F4` clears the slot's entry for every new effect. `port_fx_frame` then uses another of the pack's animations for that slot's 1171 frames, while the slot's animation is still the one recorded: 1183 a tree or bush, 1192 a rock or grassy mound (1160 frames 5..8 and 10, 1161 frames 5..7, all of 1162 and 1163), 1184 a soldier (class 1), 1.25 times the fireball's width, 1167 a vehicle (class 2) or a gun turret, 1.5 times; buildings and aircraft, and a pack without that animation, keep 1171. A plant's pictures are sized to its height as drawn (the model's width times the frame's height over its width, with Tree size), whatever their proportions. Nothing the game keeps is read or written in a way that changes it; the effect itself, its time and place, stay the game's.
- The box (`drawobj_29CCE0`, the rect the view uses to sort, to clip the canvas it saves under the sprite and for the water's reflection) is worked out from the pack's picture and width too, so a picture bigger than the game's frame or of another shape is not cut to the fireball's box.

State check: mission 7, 340 frames at 4x, a pack (30 pictures at 2x) against Off, with four enemies moved in front of the player and killed: the data object the same in every frame; in the heap the config block (G8), three pointer bytes of one block (its place in the heap) and two 12-byte blocks of SDL's thread creation. AddressSanitizer runs clean: 6x with Widescreen, Fog and Water reflection High and a 3x pack, 24 kills; 3D resolution Original with 8 pack changes during the fights; mission 15 at 2x; a broken pack (an unreadable PNG, 1 x 1 and 2000-wide pictures, a palette PNG, empty folders, folders named 99999 and abc).

## Objects pack (`port/mods/fxpack.c`, `port/mods/effects.c`, option "Objects pack")

A mod's `Objects` folder (`Mods/<mod>.zip`; `screen_objpack=<mod>`, `port_obj_pack`; guide for pack makers: docs/modding/OBJECT-PACKS.md), in the sharp view only, as the Effects pack. The trees, bushes and rocks are class 0 objects that come with the map's tiles; their pictures are the frames resources 1160..1163 (35 RSD8 bitmaps, 14 + 13 + 4 + 4, anchor 0, 0), and each frame is a different object, not a step of an animation. Their colours are mostly palette entries the planet's palette changes (17..20, 146..247), so the game shows one picture in each planet's colours.

- Loading (`load_objects`): one folder per resource, named by its number first as for effects; in it `NN.png` stands for frame NN - 1 (`01.png` the first), so a pack can replace a few frames and leave the others the game's. The pictures must be indexed PNGs (colour type 3, 8 bits a pixel, or 1, 2 or 4; not interlaced; up to 1024 per side): their colour numbers are kept as the game's palette entries (`png_indexed`: the IDAT chunks inflated with stb_image's zlib and unfiltered here, since stb_image would turn them into colours; checked against Pillow at every bit depth and filter), 0 is see-through, and the PNG's own palette is only a preview. Anything else is skipped with a line in `tnfree.log`.
- Drawing (`port_obj_frame`, from `drawobj_29AF98` for every class but 6 in the sharp view): when the pack has a picture for the frame (`ref`), a frame header of its own as for effects (FLAT8, `BMF_TRANS`, the anchor scaled), drawn by `drawobj_29BE78` through the same light table, the infrared's colour table (Sci-fi's cool plants, `port_ir_obj_clut`) and the fog's tables as the game's frame, and mirrored in the water with Water reflection High. `drawobj_29BE78` sizes the picture by the object's width in the world, so pictures exactly 2 or 3 times the game's size take the same room.
- The two packs load on one thread (`load_thread`) at the start of the next sharp drawing, each only when its choice changed.

### Tree size (`port_tree_scale` in `port/video/sharp3d.c`, option "Tree size")

Original or Realistic (`screen_trees=realistic`, `port_tree_size`), in the sharp view only. `drawobj_29ACA8` sets a sprite's width in the world (`d->scale`) for classes 0, 3 and 4; for the frames resources 1160..1163 `port_tree_scale` multiplies it by 0.6..2 picked by a hash of the object's place on the map (x and y), so each tree keeps its size from frame to frame and from game to game. `drawobj_29BE78` keeps the picture's proportions and stands it on its ground point (anchor 0, 0: the bottom's middle), so a tree grows up from where it stands; `drawobj_29CCE0`'s box uses the same width, so the view's sorting, the canvas it saves and the water's reflection follow the picture. Only the picture changes: the game's own drawing (`port_s3d_on` off; its boxes are the ones clicks use) keeps the game's sizes, and where shots hit, what the player bumps into and what can see whom never use a sprite's size, so a bigger tree can hide a unit that still shoots through it. It works with an Objects pack, the infrared, fog and light as the game's own frames.

State check: mission 3 by a wood, 150 frames at 4x with Object distance Farthest, turning among pines and bushes, the C2 test pack (pine, round bush and rocks at 2x) against a pack folder that does not exist: the data object and the game's screen the same in every frame; in the heap the config block (G8) and a sound block's pointers into other threads' memory (a second run with the pack differed from both in where SDL's audio start-up put two blocks, a timing difference of runs, not of the pack).

### Tree explosion (`port/mods/burn.c`, option "Tree explosion")

Original or Realistic (`screen_burn=realistic`, `port_burn`; called Burning plants: Off / Explosive in earlier test builds, whose `screen_burn=explosive` and `flash` still read as Realistic), on the Detail page, in the sharp view only (`port_s3d_wanted` turns it on, at 3D resolution Original too). The owner's pick of the trees thread's mock-ups, now its "Explosive v3" (owner: the leftovers stay; then: no scorch picture, the leftover behind the blast, a gradual light-up, the game's blast marks from the pack); the rules, times and colours are that thread's spec (the mock-ups' frames were 60 ms and their plant 240 pixels high; everything scales with the plant's picture). A tree's or bush's death is the fireball 1171 at the plant's place (`fx_death`, `sfx.c`); `port_fx_death` (`effects.c`) now also gets the dead object's type and place and, for a plant (the same frames as the deaths' 1183), calls `port_burn_start` with the effect object's slot, its animation, the plant's model and its width in the world. From then on the burn draws the death on the plant's own picture (the objects pack's frame when there is one, else the game's, at its Tree size) for 0.18 + 2.4 + 1.0 s of `game_time`, so it pauses with the game, and the fireball's own drawing is left out (`port_burn_hides`: `port_fx_frame` returns -1 and `drawobj_29CCE0` gives it no box) when the effects pack has a `PlantBlast` or a 1171 of its own to stand for it; otherwise the game's fireball is the blast.

- Drawing order: a burn or what is left of a plant (a "stump") is not a game entity. Each sharp drawing (`viewdist_2A0EC8` calls `port_burn_frame`, which ends the burns whose time is over) the view's square lists (`viewdist_2A13B8`) add the burns and stumps on each square (a hash of 256 chains by square) as nodes of their own (`ent` 0, `place` 0, `tmpl` 0xFF00 + the id: 0..15 a burn, 16..255 a stump; `PORT_BURN_NODE`), sorted by their distance (`viewdist_2A1840`) and drawn by `viewdist_2A250C` through `viewdist_2A2284` like an object, with the occlusion span and haze of the viewer's own square kept for each (`port_burn_span`). `port_burn_set` fills `port_burn_ent` (class 0, the plant's place) for it; `drawobj_29ACA8` gives its model (`port_burn_model`), `drawobj_29CCE0` its box (`port_burn_box`: for a burn 3 plant widths by 1.8 heights or the blast's size, room for the smoke and the flying pieces; for a stump the plant's; on below the foot by `port_burn_below` as far as the blast and its dust reach, since `viewdist_2A2284` hides an object behind nearer land only within that box: P72) and `drawobj_29AF98` draws it (`port_burn_draw`, cut to that box), so the land, buildings and nearer objects hide it as they hid the plant.
- Colour tables (`burn_draw` in `drawobj.c`): the plant's own pixels, the leftover, the char, the ash, the smoke and the pieces go through the light table of the plant's place (the same `15 - shade` row `drawobj_29BE78` would use, the fog's or the infrared's table when the canvas has one, Sci-fi's cool plant table), the sparks, the burning pieces and the glowing top through an effect's (full light; the infrared's hot one), the light-up from the one to the other (the screen's light rows between them, `View.lift`; with the infrared's or a canvas's own tables the nearer of the two), and the blast a little darker. The mixes of the palette's colours with fire, the light-up's colour and char are the palette's nearest colours (CIE Lab, as the effects pack's see-through pixels, `port_fx_near` / `port_fx_mix`), made once per palette; the pieces' colours once per palette and plant.
- The light-up (`light_up`, the first 3 frames, 180 ms; everything after it comes 60 ms later than in v2, `LU_MS`, so frame k below is at `(k + 1) x 60` ms): each pixel is mixed towards ffc878 by `fm = clamp(1.6 r - 0.6 d, 0, 1)^1.5 x 0.6`, r going from 1/3 to 1 smoothly over the 3 frames (the colours made again at each 1/32 of r), d the pixel's distance from the blast's centre (the plant's bottom middle raised by 48 of the blast's pixels, 1 at the plant's farthest pixel; worked out once in `burn_ready` into the noise's bytes `n2`, which nothing reads after), through one of 16 mixes made once per palette (`mx.lu`), and lit fm / 0.6 of the way from the plant's light to full light. So it starts at the blast's centre and spreads out.
- The burst (`shatter`, at frame 2): `cn`, the crown's pixels (the plant's that are not in the leftover) scaled to a plant 240 high, sets how much flies: 12 to 60 shards (`cn / 60`: blocks of the picture's own pixels cut to triangles, spinning, bouncing on the ground, most of them burning with sparks), 40 to 150 single pixels (`cn / 25`), 10 to 35 burnt leaves thrown high (`cn / 150`, ash flakes that flutter down through four shapes and stop on the ground) and 8 to 50 pieces of wood, bark and leaf (`cn / 120`: a random row of the effects pack's `Pieces` sheets, turned in steps of 45 degrees, bouncing, 25 % of the wood and bark and 10 % of the leaves burning). The pieces' grey is a place on the plant's own colours: two ramps made once from the plant's pixels (`ramps`: the trunk's, 7 brightness steps from 5 to 95 % of the run of pixels nearest the middle on its bottom rows, and the crown's at 15, 35, 55, 75 and 90 %). Sparks streak up for frames 2..5 (7 a frame, a line back along their motion, the head pale yellow and the tail down the fire ramp). The pack's `PlantBlast` plays at 42 ms a picture from its picture 3 (the light-up makes the start) for frames 2..20, `1.6 x sqrt(w x h)` of the plant's picture wide, standing a little below its foot, mirrored for half the plants (a bit of the seed); without it the pack's 1171 at 1.8 widths for frames 2..13. Two puffs of 1170 dust along the ground at 40 % and a plume of 1175 (no drift when the blast is mirrored). The order: the plume, the plant (what is left of it), the blast and the dust, so the blast's first pictures hide the leftover, then the shards, pieces, needles, burnt leaves and sparks on top. The mark on the ground is the game's own (the scorched squares; the pack's `BlastMarks`, below).
- What is left: the pack's leftover picture of the plant (`Leftovers/1x` or `3x`, the one the size of the plant's picture, else the 3x one), set on the plant's picture by the width, standing on its foot (`burn_ready`). It stays as it is; its broken top glows down the fire ramp for 14 frames (the pixels within `(3 + 1.5 N2) s` rows of each column's top where the smooth noise N2 is over 0.4, the noise worked out only over the rows that band can reach), and ash flakes leave its top edge for frames 2..23 (70 % a frame). The burn makes its colours once (the light-up as it grows, then the leftover) and after that only the glowing pixels again, and draws only the box of the leftover's pixels. A plant without a leftover keeps the first version's rule (the jagged trunk that chars, glows at its top and falls apart in scattered pixels, 18 % of them ash, onto a small pile at the foot that fades).
- Stumps (`stump_add`): a burn with a leftover adds one at the plant's place (up to 240; with no room the oldest whose burn is over goes; a 17th burn at a time keeps its fireball and adds only its stump). While its burn runs the burn draws it; after, the stump draws its leftover (only the box of the picture's pixels, `FxPic` `bx0..by1` from the loader). They go at the mission's start (`MissionSetup`, after `game_time = 0`) and end (`main_2451D0`), and when `game_time` goes back; they are not in the saved game.
- The pixels and shards follow the time of the frame drawn; the particles, flakes, sparks and pieces move in steps of a quarter frame (`advance`), so the look is the same at any frame rate. Random numbers and noise are per burn, seeded by the plant's place and model, so a plant burns the same way every time. Pictures the effects pack doesn't have (`PlantBlast`, `Pieces`, `Leftovers`, 1171, 1175, 1170) are left out.
- Plants that break (P92): 13 kinds of tree and bush have a broken picture, which the game shows for a plant hit for at least its hit points (and at most twice them); the next hit destroys it (`port_burn_start`'s `broken`: `fx_death` in `sfx.c` sees a type with a second model in `drawobj_cls0_models` and a dead slot, 1 when the plant stays, 2 when it is on the frame's kill list, `port_killobj_marked` in `killobj.c`). The first hit bursts the whole plant as any other and adds its stump (the pack's leftover of the plant); the entity the game keeps, as its broken picture, is marked `gone` with its place, and `port_burn_covers` leaves it out of the drawing (`drawobj_29ACA8`) while it is the same plant (the same place; cleared by `port_burn_reset`). The owner chose this over the first version (the broken picture standing, no stump of the burst's): a pine's broken picture is a few sticks. P109 (owner): the broken plant stayed in the game unseen, its dome (radius 0.2 to 0.4 squares) still pushing the player aside and stopping shots, and a second hit puffed it away; with `port_burn` on, `flash_28E040` now marks it for removal (`KillObjMark(e, 1)`, as `flash_28E350` does on the second hit) right after its death effect, so `fx_death` still sees broken 1 and the burst is whole. The game differs from Original from that hit on (the one Tree explosion change to play). When the broken picture is destroyed there is no burst: a puff of dust and smoke (the pack's 1170 and 1175, else the game's fireball; `rubble_smoke`), over the stump for a `gone` plant (`unseen`: the broken picture not drawn in the puff, no second stump); a broken picture that broke before (a saved game, Tree explosion Original) is drawn in the puff's first 200 ms and leaves the pack's leftover of that picture, if it has one, as a stump.
- Flash fire, the other pick (each pixel catching at its own time and burning with flames over scorched needles, then glowing char), was taken out on the owner's word: timed in the container it cost about 50 ms a frame more than Off with 16 trees burning at mid distance, against 13 to 18 for Explosive, most of it its simulation at the picture's full size.
- Cost: nothing new works on every pixel every frame. A burn's start takes about 1.5 ms for a 3x objects pack's pine (the picture copied, the leftover set on it, the ramps), where the first version's took about 8 (its noise over the whole picture 4.4 ms, and the colour mixes, which are the same for every plant and are now made once per palette, 1 to 3 ms for each burn). Then each frame copies its pictures to the screen (a stump only the box of its leftover's pixels) and moves a few hundred pieces.
- Memory: a fixed static arena for the pictures (`arena_get`): a block of the biggest size a burn can need (7 bytes a picture pixel, 1.75 MB) for each of the 16 burns, 29 MB in all, so every burn has room (P70: a shared 12 MB ran out at the 6th or 7th tree of a 3x objects pack). The stumps hold only their place and model (their pictures are the pack's). No heap: the game's heap stays the original's in the lockstep runs.

## Arms pack (`port/mods/arms.c`, option "Arms pack")

While the goggles' frame is over the main view (`port_ck_goggles_suit`: the frame helmet.c hands over each frame, so not the cockpit and not the drone's view), the end of the main view's sharp drawing (`port_s3d_render`, before the infrared's colours) draws the arm into the sharp picture, so the HUD and the goggles' frame stay over it. The pack (a mod's `Arms/<suit>/arms.txt`, `dist/Mods/README.txt`) is a grid of the right arm's poses for the pointer's place in the view (u, v from -1 to 1) with each pose's muzzle; the pictures are RGBA PNGs, turned into the palette's nearest colours once a palette (`port_fx_near`). They load on a thread of their own (P78), started in the cockpit view already (`port_arms_preload` from sharp3d.c with `port_ck_view_suit`); while they load the arm is not drawn. The pointer (the wide one beside the screen with Widescreen) gives u, v; the arm follows it on a spring (in steps of 10 ms; arms.txt `follow OMEGA ZETA`, 22 0.8 without it), mouselook's turn this frame (`port_mouselook_take`) adds a sway behind the turn (`sway K MAXU MAXV`, 0.06 0.3 0.2), the nearest pose is drawn shifted by the muzzle's place between the grid's poses (bilinear; below the grid the bottom row's pose moves down with the pointer, half the picture's height a unit of v, until the muzzle reaches the view's bottom edge; each picture keeps only the box of its pixels, so a pack can hold up to 512 poses; arms.txt `view X Y W H` places the view inside pictures drawn bigger than it, so a moved arm never shows its picture's edge), and the left arm is the same, mirrored. A weapon in the other arm (or none) lowers the arm drawn out of the view in 0.18 s, then the new one comes up in 0.22 s (smoothstep, its pose snapped to the pointer). Which arm: the selected weapon's record byte 1 (`port_player_weapon_mount` in pbasim.c; 2 the left arm, 3 the right, as `pbasim_28A6F0` places the shot), else none. A shot of the player (`pbasim_28A878`, real) kicks the arm back by the pack's recoil pose's muzzle move, scaled by the time between the shots lately (0.4 s or more: the whole kick on a 30 rad/s spring; quicker: down to 0.15 of it, a spring down to 10 rad/s and, while the shots keep coming, held back 0.4 x (1 - gap / 0.4) of the way, so the Laser's 0.1 s stream pulses gently). Walking (`walk BOB SWAY LEAN SPEED RATE`, 0.012 0.008 0.015 10 2.6): the suit's move on the ground since the last frame (`port_player_motion`, sharp3d.c: forward along the heading and to the right, over the game time it took; none above 0x8000 over the ground, after a jump of more than 5 m or a quarter second between) gives the speeds, smoothed on a 7 rad/s spring; the bob's phase runs on the game time of those moves (a pause holds it), half a turn a dip, RATE dips a second at SPEED or faster and down to 0.4 of that standing (not in time with the footsteps: the suits step 4 times a second walking ahead and 6.7 backing up, quick for the arm, owner): the arm is lowest at each dip (BOB x (0.5 + 0.5 cos 2 phase)), sways SWAY x sin phase, and lags LEAN behind the strafe (on the screen: mirrored for the left arm) and half of it in height behind a walk forward or back, all times the speed over SPEED (at most 1); added after the recoil, before the weapon switch's drop, so the shots leave from the muzzle where it is drawn. With "True colour" the arm's pixels clear the full-colour layer there. The player's shots leave from the arm drawn: the muzzle's place in the sharp view's pixels with the view and the sharp camera it was drawn with (`arms_shot_from`, sharp3d.c; not the game's camera, whose columns do not match the sharp view's in widescreen: P77); `port_arms_shot` (from pbasim.c's `muzzle` for the player, while that arm was drawn in the last 250 ms of game time) puts the start on the line from the eye through it (`viewdist_2A28D0`, the reticle's screen-to-world) 0x6000 along (the game's own points: 0x1000 ahead, 0x2000 aside, off the screen; nearer, a beam's band starts as thick as the arm). ## Infrared (`port/video/infrared.c`, option "Infrared")

Original or Sci-fi (`screen_infrared=scifi`). The game's infrared (`helmet.c`, `game_35ADE0` == 2, the I key) draws the 3D through the planet's colour tables into its 55 colours 0xB0..0xE6, which it sets to a ramp from white (the hottest) through yellow and brown to black (the coldest); the ground and the sky sit at the cold end, units, fires and shots in the warm part. With Sci-fi, while the infrared is on (`port_ir_on`):
- thermal colours: the display shows those 55 colours as a thermal camera's ramp: dark blue for the cold ground, purple, red, orange, yellow and white for the hottest (`port_ir_palette`, the palette only, so it works at every 3D resolution and on every renderer);
- hot outlines and the sensor look (`port_ir_sensor`, on the sharp view's picture, which `sharp3d.c` draws at Original too while the infrared is on): a pale yellow ring up to 4 pixels wide around the pixels of 0xCF or hotter, faint lines on the game's rows, a moving grain and a sweep line going down the view every 5 seconds, all as steps along the same ramp; the sweep is a thin line and a trail a tenth of the view's height, fading.
- cool plants (`port_ir_obj_clut`, from `drawobj.c`): the game draws the trees, bushes and other scenery (class 0) through its infrared tables like the units, and their brightest texels land in the warm part (0xCF and hotter), so the outlines ringed specks on every tree. With Sci-fi a scenery object's table is clamped to 0xD2 at the warm end (cached for the last 4 tables), so trees stay cool and only units, fires and shots glow.
- cool ground (`port_ir_land_clut`, for the far land's columns in `haze.c` with the camera's table, the squares in `weather.c` and the fog's rows in `port/video/fog.c`): a few land texture colours land in the warm part of the camera's table too (in the original as well), and the outlines turned each such texel on far hills into a bright speck. With Sci-fi the land's table is clamped the same way (made again when the table changes), so the ground stays cool (P53).
The game's own picture and everything it reads stay the original's. True colour is off in the infrared (Original and Sci-fi: its colours are not the infrared's). With Fog on, the infrared is fogged too, along its own ramp (Fog, P49).

## Smooth videos (`port/video/videosmooth.c`, `tnfree-rife.dll`)

The game's 87 movies run at 15 pictures a second. "Smooth videos" makes the picture halfway between each two with RIFE 4.6 (a neural network for frame interpolation) on the graphics card, so they play at 30. Nothing is downloaded or shipped from the game: the pictures are made from the player's own movies while they play.

- `tnfree-rife.dll` (`rife/`): nihui's rife-ncnn-vulkan (`third_party/rife-ncnn-vulkan`, MIT) on ncnn with Vulkan, behind the C interface of `port/include/tnfree_rife.h`. C++, about 9 MB, so it is a separate file that `tnfree.exe` loads only when the option is on. It imports `vulkan-1.dll` directly: without Vulkan drivers it does not load, and the option stays off.
- ncnn is pinned to a July 2022 commit (`b4ba207`): newer ncnn ran RIFE about 25 times slower on AMD integrated graphics (owner's test, 32- and 64-bit alike); the 2022 version runs 15 to 30 fps movies in real time there. The build fetches ncnn (with its glslang) and Vulkan-Headers with git at fixed commits, makes the `vulkan-1.dll` import library from `rife/vulkan-1.def`, and downloads the model files with a SHA-256 check into `RIFE/rife-v4.6` next to `tnfree.exe`. Offline: `TNFREE_NCNN_DIR`, `TNFREE_VULKAN_HEADERS_DIR`, `TNFREE_RIFE_MODEL_DIR`.
- Local changes to rife-ncnn-vulkan: `%ls` for the wide model paths in `rife.cpp` (MinGW's `swprintf` reads `%s` as a narrow string, so the model never loaded); `main.cpp` (the command-line program) is not used.
- Playback (`port/video/smacker.c`): the game's own decoder and what the game sees stay as they are. A second decoder of the same file runs one picture ahead, video only, and hands each picture to `videosmooth.c`, which turns it into RGB, skips scene cuts and unchanged pictures, and queues the pair for a worker thread that owns the DLL. In each in-between picture the 4x4 blocks that are the same in both pictures keep their own pixels ("keep still parts"): RIFE softens still areas a little, which flickered against the sharp real pictures. Measured on 5 clips (each in-between picture of a 7.5 fps copy compared with the real one): never worse, briefings 36.2 to 42.0 dB; RIFE's TTA mode (+0.1 to 1 dB for 3 to 8 times the work) and RIFE on the movie at twice its size (worse in every clip) were tried and left out. Newer RIFE models (4.15, 4.15-lite, 4.22, 4.22-lite, 4.25, 4.25-lite, 4.26, from TNTwise's rife-ncnn-vulkan, MIT) measured the same way: 4.15 is the best on these movies (+0.4 dB on average with keep still parts, +1.2 dB on the intro's dropship), the ones from 4.22 on are a little worse than 4.6 (they are tuned for filmed and drawn video). Softening the dithered pictures before RIFE (a 0.7 pixel blur, "dither filter") helped only the dropship and made every other movie softer and worse (briefing 1: 36.2 to 25.3 dB, 41.3 with keep still parts), so it is left out. `smooth-test --model rife-v4.15` (any folder in `RIFE/`) tries another model; the DLL pads the picture as each model needs. While the game waits for its next picture (SmackWait), the in-between picture is due halfway; one not ready a quarter of a picture later is skipped (the earlier picture stays). `vsmooth_show` puts the picture up; the display (`present`, main thread) draws it in RGB over the movie's place in the game's screen texture, through the same colour settings as the palette (`port_screen_grade_rgb`), until `SmackDoFrame` copies the movie's next picture (`vsmooth_hide`) or the palette changes. The setting is on the Sound & movies page (`smooth_videos=30` in `tnfree.ini`; turning it on loads the DLL in the background, so the next movie is smoothed). `FREEFALL_SMOOTH_WAIT=1` makes the movie wait for each in-between picture (tests on a slow card such as lavapipe); the log gets one line per movie (pictures made, time each, scene cuts, skipped, late).
- `tnfree --smooth-test [--gpu N|integrated|discrete] [--model M] [--out DIR] [MOVIE ...]` (`port/test/smoothtest.c`, not in the package; for tests): smooths movies into Motion JPEG AVI files in `SmoothTest` next to `tnfree.exe` (left as the game shows it, right smoothed, at the movie's own size) with `results.txt` (card, time per picture).

## Options presets and mod sets (`port/ui/options.c`, `port/video/screen.c`, `port/mods/fxpack.c`)

The options screen is a table of pages (`pages[]`: `Entry` lines of kind `E_OPT` for options.c's own settings, `E_SCR` for screen.c's `S_*` settings, `E_PAGE`, `E_GAP`, `E_BACK`, `E_CLOSE`), each page's Back / Esc going to `page_parent[]`; `psel[]` keeps the chosen line of each page. A screen.c line that needs another setting is drawn grey (`port_screen_usable`: Anti-aliasing and Map smoothing need 3D resolution, Water ripples and Water effects Water reflection Medium or High, Cockpit pack Widescreen) and can still be changed.

The presets are not stored: `preset_now` compares the settings with each preset (options.c's frame rate, controls style, Auto target camera, Target label, Map view cone, Show enemies without MFD (Freefall only), Auto-aim's box (5 pixels in Vanilla+ and Freefall, 20 in Classic), Auto-aim highlight (Freefall only), `port_screen_is_preset` for screen.c's, and the mod set), so any change shows Custom and choosing a preset again goes back. `apply_preset` sets them (`port_screen_preset`); Smooth videos' RIFE model starts loading at once in the background (`vsmooth_start`), and while it loads, or the GPU renderer that FXAA needs is still being switched to (`port_renderer_switching`: the renderer wanted is not the one running), the Preset line shows "(starting...)". Mouse sensitivity, Invert mouse, the keys, the filters, Show FPS, Radar without MFD, the music device and the music pack are not part of any preset.

First start: with no `controls=` and no `mouselook=` line in `tnfree.ini` (`main.c`), the options screen opens on its welcome page (`PG_WELCOME`, Esc does nothing there) once the game's own menu has been up for a second: 640 x 480, no movie open (`port_movies_open`, counted by `SmackOpen` / `SmackClose` in `port/video/smacker.c`; the look-ahead decoder of Smooth videos is not counted), not in lockstep or the benchmark. Test scripts (`FREEFALL_SCRIPT`) skip it unless `FREEFALL_WELCOME=1`; `--preset` skips it and applies that preset.

A mod (a mod set) is one zip in `Mods` with one or more kind folders in it, `Cockpits`, `Arms`, `Effects` or `Objects` (`port_mod_sets`); while it is being made it can be a folder of the same name, which comes before the zip. There are no kind folders in `Mods` (owner: they only confuse people; `dist/Mods/README.txt` is the zip's layout). The pack name of each kind is the mod's name: `port_pack_dir` gives `Mods/<name>/<kind>` when that folder is there, else `Mods/<name>.zip/<kind>`, so the loaders (`fxpack.c`'s `load_pack`, `cockpitpack.c`, `arms.c`) and `tnfree.ini` (`screen_cockpit=<mod>` and so on) take a mod's name as a pack's, and each kind's list (`list_packs`) holds the mods that have that kind. The Mod set line shows a set's name when all four packs are that set's (a kind the set lacks Off), Off when all are Off, else Custom; `mod.txt` (`name`, `version`, `author` lines) gives its help line. Music packs stay in `Music` (owner's choice); a pack there can be a zip too (`Music/<pack>.zip`, its files at the top or in one folder, listed with `port_zip_files`, a folder of the same name first; `musicpack.c`).

Zips (`port/mods/modzip.c`, owner's ask): a path through a zip (`Mods/Freefall.zip/Effects/1171/01.png`) is read from it: `port_mod_load` (stored or deflated members, inflated by stb_image's `stbi_zlib_decode_noheader_buffer`), `port_mod_type` and `port_mod_list_zip`, which `fxpack.c`'s `list_dir`, `load_*`, `port_png_*`, `cockpitpack.c` and `arms.c` use for every pack file. Each zip's central directory is read once (again when its size or time changes) and the leading folders are dropped: those above the first kind folder within three levels (`Freefall/Cockpits/...`, `Mods/Freefall/Cockpits/...`); members outside them are left out. The list is guarded by a mutex (the effects pack loads on its own thread); each read opens the file on its own. Zip64 and encrypted members are skipped.

## Auto-aim (`hudmain.c`, `options.c`)

The game's auto-aim: `hud_reticle` (`hudmain.c`) hands the locked target (`targ_current`, while `hud_35A944`, always 1) to `reticle_target` only when `hud_aim_on_target` says the pointer is within 20 pixels across and 20 up and down (40 with the goggles) of the target's box; a click in a side screen's 3D view (`hview3d_274570`, `hview3d_274C30`) hands it whatever the pointer. `reticle_target` turns the pointer into the point 10 squares from the eye along its line (`viewdist_2A28D0`) and fires (`pbasim_28A878`, `weapon_fire`); with a target `weapon_fire` aims at the target's centre (`interact_298864`) instead, and `aim_solve` (`weapphys.c`) leads it by its speed for a beam (`aim_lead`) or lobs onto it, raised by `biped_27ED34`, for a grenade or missile (`aim_lob`, `ord_table[type].ray == 0`). `hud_status_ticks` doubles the target's top and bottom ticks while a shot would go to it.

"Auto-aim" (`port_aim_box`, `auto_aim=20|5|off`, the owner's steps): the box's half size in game pixels, 20 the game's (the Classic preset), 5 (Vanilla+, Freefall), or 0 for Off. 20 needs the Classic controls style (owner): with Advanced the line steps only 5 and Off, and a 20 kept from Classic shows grey (`opt_dim`: grey, but Left/Right still change it) and works as 5 (`port_aim_box_now`). `hud_aim_on_target` takes the box in force in place of its 20 (doubled up and down with the goggles, as the game's), in the game's own view and the wide one, so `hud_reticle` and the doubled ticks follow it; Off (0) also hands no target in the side screens' clicks (`hview3d.c`), which otherwise use the lock wherever the pointer is. Checked in mission 19 (lockstep, gdb on `weapon_fire`): a shot takes the lock exactly while the pointer is less than the box's size from the box's centre across and up and down (20: 13 pixels yes, 22 no; 5: 1 to 3 yes, 5 no; Off: never). Nothing in the game's state changes; for co-op the setting will have to be one for all. (A first version had a Lead marker instead, a diamond where to point for an unaimed shot to hit; the owner found it out of place in this game.)

"Auto-aim highlight" (`port_aim_sign`, `aim_highlight=on|off`, On only in the Freefall preset; grey with Auto-aim Off): `port_hud_aim_sign` (`hudmain.c`) changes the pointer while `hud_reticle`'s test holds (a lock, the player's own view, no map, `hud_aim_on_target`) and the pointer is in the main view. The 3D views' crosshair is frames 0-10 of the pointer resource 505 (`RESHELM` / `RESHLMHI`; 1-10 add the turn arrows), set by `hview3d_2754FC` and by the main pane's mouse events (`hud_268D80`, 0x40 / 0x80); the highlight runs right after both and once a frame (`hud_26A188`, code 2), so the game's reset never shows. It is a copy of the frame in use with its bright green (0x89) in the red (0x44) of the HUD's cross pointer (frame 0x16), put in with `MouseSetCursorBitmap` (the game's, unused by it; `tnm_cursor_ref` 0 marks it); the crosshair comes back with `MouseSetCursor`. Only the pointer's picture changes. (A test build also had a Red cross choice, the HUD's pointer itself; the owner kept the red centre only.) A `tnfree.ini` without the line (and without a test build's `aim_sign=cross|centre`) gets On when its other settings are the Freefall preset's (`port_options_aim_legacy`).

## Help screen (`port/ui/help.c`)

H (or ?) in a mission runs the game's help screen (`options_2CCC28`, `src/game/shell/options.c`: it pauses the mission, shows RESGAME.RES 0x187 in 640 x 480 and closes on a key or a click). With the Classic preset's settings that is all (`port_help_wanted`, `port/ui/options.c`: `preset_now() != 0`). Otherwise the display draws Freefall's help screen over the game's (`port_help_present`, called by `present` right after the screen is drawn):
- The picture: `port_help_open` (game thread, first thing in `options_2CCC28`) asks the display to read the window back and waits for it, at most 300 ms, while the mission's screen is still up; `present` reads back the rectangle the screen's picture went to (with Widescreen the stretched rectangle, with a cockpit pack the pack's) and notes where the game's own 320 columns are in it.
- The callouts: the places of the HUD's parts on the game's 320 x 400 screen, per suit for the cockpit (`cockpit_at`) and for the goggles (`goggles_at`: one table for Scout, Standard and Heavy, one for the Pirate), measured in missions 1 (Scout), 3 (Standard), 9 (Heavy) and 39 (Pirate); which one comes from the cockpit pack's note of the art up (`port_ck_view_suit`, `port_ck_goggles_suit`). A part a suit lacks gets its label without a line.
- The text: every key is the action's binding in the current controls style (`port_keys_bound`, `port/ui/keys.c`; `{action}` in the line specs), a middle button or a wheel drawn as the mouse. The screen is laid out at 1920 x 1080 and drawn on the CPU at the window's scale (Liberation Sans, built into the exe by `tools/embed.py`; stb_truetype; the title is the options screen's logo line, `port/res/logo-line.png`, each window pixel the average of the logo's pixels under it) into two textures: everything around the picture (`draw_base`: drawn ahead by `base_ahead` on a thread of its own, a look twice a second while the help screen is not up, and again only when the window's size, the controls style or the bindings change; not in lockstep runs or `--bench`), and over the picture its frame, the callouts' lines and the view's box (`draw_pic`, on a clear texture as big as the picture's room, kept until the picture's place or the suit changes). Opening the screen only reads the window back (P117). `port_help_renderer_gone` lets go of the textures when the renderer is made again.
- H on it (`port_help_key` from the help screen's key handler `options_2CCB38`) shows the game's own instead; the press that opened the screen never reaches that handler, and the game's keyboard handler drops a held key's repeats. Any other key or a click closes it as before.
- While the help screen is up the screen is not stretched for Widescreen (P87).
Test: `FREEFALL_LOCKSTEP_INPUT="30:t23"` opens it at frame 30 (the help screen's frames run fast in lockstep, so a second H a moment later needs a frame number in the tens of thousands); `FREEFALL_SHOT_WINDOW=1` keeps the window's shots.

## Files built into tnfree.exe, and the release folder (`tools/package.sh`)

The help screen's fonts, the Freefall logo, the wide main menu's sides (`tools/embed.py`, C arrays)
and the options screen's preview pictures (`dist/Previews`, `tools/embed_previews.py`) are built
into `tnfree.exe`, so the release folder holds nothing but what a player may open or change. The
previews are many and large (about 2.5 MB of JPEGs): the generated `previews.S` takes each file in
as it is with `.incbin` (`.rdata` on Windows, `.rodata` elsewhere; the symbol prefix as
`gen_port.py`'s), and `previews.c` lists them by name (`port_previews`). A picture added to
`dist/Previews` is found by the CMake glob at the next build. `pic_get` in `port/ui/options.c`
reads `Previews/<name>.jpg` or `.png` next to `tnfree.exe` first, so new stills can be tried
without a build.

The GeneralUser GS SoundFont (S. Christian Collins, licence v2.0) goes into the release's Music
folder but is not kept in git: `tools/fetch-generaluser.sh` downloads it, with its licence, from
one pinned commit of the author's GitHub and checks both files' SHA-256 (the `build` workflow runs
it before packaging; `tools/package.sh` takes its folder as the third argument). A new version of
GeneralUser GS means a new commit and new hashes in that script, and its THIRD-PARTY entry.

The Freefall Music pack (`Freefall-MP3.zip`, the game's music as MP3 by Rich "Weeds" Nagel, shared
with his permission) goes into the release's Music folder the same way: it is a file of this
repository's release `music-mp3-1` (the owner made it; a session cannot), and
`tools/fetch-freefall-files.sh` downloads it (with `gh api` and the build's token, so it works while
the repository is private) and checks its SHA-256. A new version of the pack means a new release
tag and hash in that script. The Freefall preset chooses it as the Music pack when it is in Music
(`preset_music` in `port/ui/options.c`; the list of packs read at most once a second, as the mod
sets'), Vanilla+ and Classic choose Off.

The Freefall Mod Pack (`Freefall.zip`, the project's cockpits, goggles, arms, effects and trees,
version 1.2) goes into the release's Mods folder the same way, from the release `mod-pack-1.2`, by
the same script. Its art is made from the game's own pictures (its README says so), which is why
it is a release file and never in git. The Freefall preset already chose the mod named Freefall
when it is in Mods; nothing in the code changed for it.

## Known work

- Frame rate: limited to 25 frames a second (`--fps`). The game's projectile hit test fails above about 30 (`EDMS_FF_cast_projectile` collects the objects along the ray in whole steps of 16 projectile diameters, rounded down, so a short move tests none). With `--fps` above 25 (or 0) `port_highfps_fix` counts the last part step too (`src/edms/ff_ftl.c`); at 25 nothing changes.
- General MIDI on Linux and macOS (only Windows has a system synthesizer through `midiOut`).
- Only MinGW-w64 GCC is tested. Clang should work. MSVC can't compile GNU C extensions and GNU assembler syntax; supporting it means generating MASM for `tn_image.S` and removing the remaining inline asm.
- 64-bit (step 5): struct layouts assume 32-bit pointers.
